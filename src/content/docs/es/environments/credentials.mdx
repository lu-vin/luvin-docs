Un contrato dice en sus `securitySchemes` cómo está protegida su API: una API key en un header, un token Bearer, un usuario y contraseña. La sección **Credenciales** del ambiente te pide un valor por esquema, así cada ambiente puede usar su propia clave o su propio token.

## Ejemplo: la tienda y el sandbox de PayPal

El contrato de la tienda protege sus operaciones con dos esquemas, `shopKey` (una API key en el header `X-Shop-Key`) y `shopBearer` (un token Bearer). Abre el ambiente `staging`:

| Campo | Tipo que se ve | Ayuda |
|---|---|---|
| `shopKey` | `apiKey · header "X-Shop-Key"` | *API key · fuente shop* |
| `shopBearer` | `bearer` | *Token Bearer (se envía como Authorization: Bearer …) · fuente shop* |

La etiqueta de la sección dice **0/2 completas**, en ámbar. Pega la clave en `shopKey` y escribe `{{shopToken}}` en `shopBearer`, un secreto que ya tienes. La etiqueta se pone verde: **2/2 completas**. Un paso protegido sale ahora con `X-Shop-Key: <tu clave>` y `Authorization: Bearer <el valor de shopToken>`.

El ejemplo de PayPal funciona distinto. Su ambiente `Sandbox` muestra una credencial, `oauth2`, en **0/1 completas**, y está bien: los workflows de PayPal obtienen su token desde la pestaña **Autorización** del workflow, que usa `{{clientId}}` y `{{clientSecret}}`. Una credencial solo hace falta cuando nada más autoriza la llamada.

## Qué credenciales se listan

Luvin lista los esquemas de seguridad de las operaciones que llaman tus workflows. Un esquema que ningún paso usa no aparece.

| Detalle | Qué ves |
|---|---|
| Un campo por contrato y esquema | La etiqueta es el nombre del esquema, como `shopKey`. Cuando dos contratos usan el mismo nombre de esquema, la etiqueta empieza con la fuente: `shop · shopKey`. |
| El tipo | `bearer`, `basic`, `apiKey`, `oauth2` u `openIdConnect`. Una API key muestra también dónde va y su nombre: `apiKey · header "X-Shop-Key"`. |
| La ayuda | Qué pegar, y la fuente a la que pertenece. |
| Una operación con varias alternativas | Luvin usa la primera que no esté vacía. |
| Ningún esquema | *Los contratos no declaran `securitySchemes`. Si la autenticación va en headers o en un paso del workflow, se toma de los inputs.* |

Cualquier otro tipo, como `mutualTLS`, dice *Tipo de seguridad no soportado; se ignorará*.

## Completa una credencial

<Steps>

1. Abre el ambiente: haz clic en la mitad izquierda de la pastilla de arriba a la derecha (el ambiente de la colección) y elige **Configurar ambiente…**.
2. En **Credenciales**, busca el esquema.
3. Pega el valor, o escribe un secreto como `{{apiKey}}`. El texto de ejemplo te lo recuerda: *Pega el valor o usa un secreto: `{{apiKey}}`*.
4. Mira la etiqueta, por ejemplo **1/2 completas**. Está en ámbar mientras falta una y en verde cuando están todas.

</Steps>

| Tipo | Qué pegar |
|---|---|
| `bearer` | El token, sin `Bearer `. |
| `basic` | `usuario:contraseña`. El texto de ejemplo lo dice. Luvin lo codifica en Base64. |
| `apiKey` | La clave. |
| `oauth2`, `openIdConnect` | Un access token. Se envía como Bearer. |

Un valor pegado queda oculto como una contraseña. Un valor que empieza con `{{` se ve en claro, con los [colores de las variables](/es/environments/suggestions/), porque es un nombre, no el secreto.

<Aside type="tip" title="Apunta a un secreto">
Escribir `{{apiKey}}` en la credencial y guardar el valor en **Secretos** te deja reutilizar la misma clave en un request suelto y en la autorización del workflow. La credencial y el secreto quedan sincronizados.
</Aside>

## Dónde se usan las credenciales

| Dónde | ¿Las envía? |
|---|---|
| Pasos de un workflow, contra la **API real** | Sí, en cada paso cuya operación pide ese esquema. |
| **Try it out** en un contrato | Sí. Dice *Se envían las credenciales del ambiente (shopKey, shopBearer).* |
| La documentación del contrato | Sí. Swagger UI empieza autorizada con ellas: API key, bearer, basic y un token de OAuth 2.0 pegado. |
| Un paso que ya pone el header | No. Un paso con su propio header `Authorization`, o con el parámetro de la API key, conserva su valor. |
| Un workflow con su propia autorización | No. Cualquier opción distinta de **Del contrato** en la pestaña **Autorización** las reemplaza. Mira [Autorización de un workflow](/es/authorization/workflow/). |
| Casos que prueban una llamada sin credenciales | No, a propósito. |
| **Simulación** | Ninguna llamada sale de tu equipo. |
| Requests sueltos | No. Un request usa su propia pestaña **Autorización**, o la de la colección. |

Para ver cómo sale cada tipo en la llamada, mira [Credenciales del contrato](/es/authorization/contract-credentials/).

## Cómo se guardan las credenciales

- Cifradas en este equipo, como los secretos. Nunca se escriben en el archivo del ambiente.
- Son de un ambiente. Un ambiente nuevo no las copia.
- Se borran de este equipo junto con su ambiente.
- Se tapan como `••••` en resultados, reportes y Dev Tools.
- Después de clonar el workspace, cada persona completa las suyas.

## Cuando falta una

Antes de ejecutar contra la **API real**, Luvin revisa los pasos del workflow. Si un paso necesita una credencial vacía, y ni el paso ni la pestaña **Autorización** la ponen, aparece un aviso sobre el workflow:

*Faltan credenciales en «staging»: las llamadas que las necesitan responderán 401.*

Haz clic en **Completar** para abrir el ambiente. El runner muestra el mismo aviso para los workflows que marcas. **Try it out** dice *Faltan credenciales en «staging»: la API probablemente responderá 401.*, con **Configurar**.

Igual puedes ejecutar. Las llamadas que necesitan la credencial salen sin ella, y la API suele responder `401`.
