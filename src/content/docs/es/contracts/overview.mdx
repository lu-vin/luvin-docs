Un contrato es un archivo que describe una API: qué llamadas tiene, qué recibe cada una y qué responde. Luvin lee dos tipos, **OpenAPI** (APIs REST) y **AsyncAPI** (mensajes y eventos). Sin un contrato, Luvin no sabe qué operaciones existen, así que no puedes diseñar un workflow a partir de ellas.

Luvin nunca cambia un contrato por su cuenta. Diseñas, ejecutas y simulas workflows, y el contrato queda como lo escribiste. Solo cambia cuando tú lo editas.

## Ejemplo: una operación del contrato de la PokéAPI

Este es un fragmento recortado de `examples/pokemon/pokeapi.openapi.yaml`, incluido con Luvin:

```yaml title="pokeapi.openapi.yaml"
servers:
  - url: https://pokeapi.co/api/v2
paths:
  /pokemon/{idOrName}:
    get:
      operationId: getPokemon
      summary: Consulta un Pokémon
      parameters:
        - $ref: '#/components/parameters/IdOrName'
      responses:
        '200':
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Pokemon' }
              example:
                id: 25
                name: pikachu
                types:
                  - slot: 1
                    type: { name: electric }
        '404':
          $ref: '#/components/responses/NotFound'
```

Esta única operación es lo que Luvin necesita para diseñar, ejecutar y simular una llamada:

| En el contrato | Qué hace Luvin con eso |
|---|---|
| `operationId: getPokemon` | La lista en la pestaña **Diseño**, lista para arrastrarla al lienzo. El paso nuevo se llama `getPokemon`. |
| `summary` | Pasa a ser la descripción del paso. |
| `parameters` | Pide `idOrName` en el paso. Como es obligatorio y nada le da un valor, se vuelve un input del workflow. |
| `servers` | Completa la URL base `pokeapi` de cada ambiente con `https://pokeapi.co/api/v2`. |
| `200` con su `schema` | Define el criterio de éxito `$statusCode == 200`, ofrece los campos de la respuesta como outputs y compara cada respuesta real con el schema. |
| `example` del `200` | Es la respuesta en **Simulación** y en un mock server. |
| `404` | Se ofrece como un error que el paso puede manejar, por ejemplo para terminar el workflow. |

## Qué lee Luvin de un contrato

| Parte del contrato | Dónde la ves | Más información |
|---|---|---|
| `paths` y sus operaciones | La búsqueda de **＋ Paso** en la pestaña **Diseño**. Cada operación se vuelve un paso. | [De la operación al paso](/es/contracts/operations-and-steps/) |
| `parameters` y `requestBody` | Los parámetros y el body de cada paso, los inputs del workflow y los casos generados. | [Schemas, inputs y casos](/es/contracts/schemas-and-cases/) |
| `responses` y sus schemas | Criterios de éxito, ramas de error, outputs y la comprobación de cada respuesta. | [¿La respuesta cumple el contrato?](/es/contracts/response-check/) |
| `example` y `examples` | **Simulación**, mock servers, **Try it out**, requests generados y los valores de partida de los inputs. | [Ejemplos, simulación y mocks](/es/contracts/examples/) |
| `servers` | Las **URLs base** de cada ambiente. | [Servidores y credenciales](/es/contracts/servers-and-credentials/) |
| `security` y `securitySchemes` | Las **Credenciales** de cada ambiente y el caso **Sin credenciales**. | [Servidores y credenciales](/es/contracts/servers-and-credentials/) |
| `tags` | La búsqueda de **＋ Paso**, y una carpeta por tag cuando generas requests. | [Generar requests desde un contrato](/es/requests/generate-from-contract/) |
| `channels`, `operations` y mensajes de AsyncAPI | Pasos send y receive, siempre simulados. | [Contratos AsyncAPI](/es/contracts/asyncapi/) |
| `$ref` a otros archivos | Las partes que viven en otros archivos, unidas en un solo contrato. | [Referencias entre archivos](/es/contracts/references/) |

## Cómo encuentra un workflow su contrato

Un archivo de workflows (el archivo Arazzo) lista los contratos que usa en `sourceDescriptions`. Cada uno tiene un nombre, una dirección y un tipo:

```yaml title="pokemon.arazzo.yaml"
sourceDescriptions:
  - name: pokeapi
    url: ./pokeapi.openapi.yaml
    type: openapi
  - name: pokedexEvents
    url: ./pokedex-events.asyncapi.yaml
    type: asyncapi
```

Los pasos usan ese nombre: `operationId: $sourceDescriptions.pokeapi.getPokemon`. La URL base del ambiente y las credenciales también se guardan con ese nombre, así que `pokeapi` es el nombre que ves en la lista **Contratos**, en **＋ Paso** y en el ambiente.

Luvin empareja cada dirección con un archivo de la colección por su nombre de archivo. No escribes estas líneas a mano: un archivo de workflows nuevo lista por ti todos los contratos de la colección. Mira [Cómo encuentra su archivo un workflow](/es/contracts/add/#cómo-encuentra-su-archivo-un-workflow).

## Versiones soportadas

| Tipo | Versiones | Con otra versión |
|---|---|---|
| OpenAPI | 3.x, por ejemplo `openapi: 3.0.3` | Swagger 2.0 se abre y aparece en la lista, con la advertencia *Es Swagger 2.0: Luvin trabaja con OpenAPI 3.x; conviene migrarlo.* Partes de él pueden no funcionar como esperas. |
| AsyncAPI | 2.x y 3.x | El editor advierte *Versión de AsyncAPI «x»: se espera 2.x o 3.x.* |

Luvin reconoce el tipo de un archivo por sus primeros campos: `openapi:` o `swagger:` para OpenAPI, `asyncapi:` para AsyncAPI. Un archivo YAML o JSON sin ninguno de los dos, como un archivo de schemas compartidos, aparece como `schemas`. El nombre del archivo no decide el tipo, pero nombres como `pokeapi.openapi.yaml` hacen la lista más fácil de leer.

<Aside type="tip">
Puedes probar una API sin contrato: envía requests sueltos y arrástralos a un workflow. Luvin arma entonces por su cuenta un contrato pequeño con tus requests. Mira [Armar desde requests guardados](/es/design/from-requests/).
</Aside>
