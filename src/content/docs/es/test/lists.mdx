Muchas APIs devuelven listas: las tarjetas de un cliente, los productos de un catálogo. Cuando un paso posterior necesita datos de esa lista, Luvin pausa la ejecución y te muestra lo que llegó, para que elijas con qué probar.

<video controls muted playsinline preload="metadata" poster="/media/es/list-pick.webp" src="/media/es/list-pick.mp4"></video>

## Ejemplo: Pokemon card contra la API real

El primer paso de **Pokemon card** devuelve dos listas que usan los pasos siguientes: `types` (1 elemento) y `abilities` (2 elementos). Contra la API real la ejecución se pausa por las dos, también por `types` con su único elemento: ves lo que devolvió el servicio y confirmas con qué sigue. En Simulación se pausa solo por `abilities`, la lista que tiene entre qué elegir.

<Steps>
1. Elige **API real** y pulsa **Ejecutar**.
2. El diálogo se abre por `types`, con su único elemento. Pulsa **Continuar con este elemento**.
3. Se abre de nuevo por `abilities`, que tiene dos elementos. Haz clic en el que quieras y pulsa **Continuar con este elemento**.
</Steps>

Contra la API real el diálogo aparece por cada lista que usan los pasos siguientes, aunque tenga un solo elemento. En **Simulación** aparece solo cuando la lista tiene dos elementos o más. Para una versión paso a paso, mira la receta [Elige un elemento de una lista](/es/recipes/list-pick/).

## Elige y continúa

<Steps>
1. Ejecuta el caso. Después del paso que devuelve la lista, se abre un diálogo con el título **¿Con qué dato de la lista quieres probar?**
2. Lee la parte de arriba del diálogo: qué paso devolvió la lista y cuántos elementos, el **Caso** que se está ejecutando y **Lo recibe**, los pasos y parámetros posteriores que reciben el dato.
3. Haz clic en la fila del elemento que quieres.
4. Pulsa **Continuar con este elemento**. Los pasos siguientes se ejecutan con él.
</Steps>

![El diálogo para elegir un elemento de la lista que devolvió un paso](/media/es/list-pick.webp)

La tabla muestra los elementos reales de la lista:

- Las columnas marcadas **se usa** contienen los valores que pasan a los pasos siguientes.
- Con más de 8 elementos aparece una caja de búsqueda, **Buscar en la lista…**. También busca en los campos que no se muestran como columnas.
- Si los elementos tienen más campos de los que caben en la tabla, el encabezado dice cuántos, por ejemplo **+4 datos**. **Ver todo** en una fila abre el elemento completo.
- <Badge text="Máx. 200 elementos" variant="caution" /> La tabla muestra hasta 200 elementos. Busca para encontrar el resto.

## Lo que puedes elegir depende del diseño

| Cómo usa el workflow la lista | Qué ofrece el diálogo |
|---|---|
| Un valor de un elemento va a un parámetro de ruta, query o header | Un elemento |
| Un valor de un elemento va dentro de una lista del body del request siguiente | Varios elementos, o **Enviar toda la lista**. El body recibe una entrada por elemento |
| La lista completa va a un paso que recibe listas | **Enviar toda la lista**, o **Elegir elementos** para enviar solo algunos |
| La lista completa se conecta a parámetros de un solo valor | Un elemento. Cada parámetro recibe un campo de ese elemento |

![El diálogo que ofrece enviar toda la lista o elegir elementos](/media/es/list-pick-many.webp)

Cuando marcas varios elementos, el botón dice **Continuar con N elegidos**. Si un paso posterior recibe un solo valor, toma el primero de los elegidos, y el diálogo lo avisa.

En el último caso de la tabla, el diálogo agrega **Qué recibe cada paso del elemento que elijas**. Luvin empareja cada parámetro con el campo de nombre parecido: `bank` toma el `bank` del elemento. Para usar otro campo, cámbialo en el menú desplegable junto al parámetro.

## Prepáralo en el diseño

<Steps>
1. En la pestaña **Diseño**, haz clic en el paso que necesita el dato.
2. En la pestaña **Datos** del panel del paso, en **Recibe**, abre el origen del parámetro y elige el campo de la lista del paso anterior, por ejemplo `activeCreditCards/bank`. Dice *de una lista: eliges cuál al ejecutar*.
3. Ejecuta el caso. El diálogo aparece después del paso que devuelve la lista.
</Steps>

Un campo que viene de una lista se nombra sin su posición: `activeCreditCards/bank`, no `activeCreditCards/0/bank`. Mira [Conecta datos entre pasos](/es/design/wire-data/).

## Una lista que devuelve un workflow llamado

Un paso puede llamar a otro workflow, por ejemplo uno que reutilizas para traer las tarjetas de un cliente. Si ese workflow devuelve una lista como output, y el paso siguiente la pone en un parámetro de un solo valor, la ejecución se pausa igual. Pregunta el paso que llamó al workflow, y cada parámetro recibe su dato del elemento elegido: `bank` recibe el `bank` de la tarjeta elegida, `id` recibe el `id` del beneficio elegido. Sin nadie que elija (el runner o una prueba de carga), se usa el primer elemento.

## Varios casos a la vez

Cuando ejecutas varios casos, el diálogo ofrece **Usar esta elección en los demás casos de esta ejecución**. Déjalo marcado para que se te pregunte una sola vez. Desmárcalo para elegir en cada caso. Si un caso posterior recibe una lista sin los elementos que elegiste, el diálogo vuelve a preguntar.

Luvin recuerda tu última elección y la propone la próxima vez que ejecutes.

## Reglas para las próximas veces

Para que el diálogo no pregunte cada vez, guarda una regla. La regla elige por ti en las próximas ejecuciones, y es la que usa el [runner](/es/runner/workflows/), donde no hay nadie para responder.

<Steps>
1. Ejecuta el caso. Se abre el diálogo.
2. Abajo, abre la lista **Las próximas veces:** y elige una regla.
3. Elige el elemento para esta ejecución como siempre y pulsa **Continuar con este elemento**.
</Steps>

![La parte de abajo del diálogo con la lista Las próximas veces: abierta: Preguntarme, Usar el que dice el diseño, Elegir uno al azar, Uno distinto en cada vuelta y El que cumpla…](/media/es/list-pick-rule.webp)

| Regla | Qué elige |
|---|---|
| **Preguntarme** | No se guarda nada: el diálogo vuelve a preguntar. En el runner se usa el elemento que dice el diseño. |
| **Usar el que dice el diseño** | El elemento al que apunta el diseño del workflow. |
| **Elegir uno al azar** | Cualquier elemento, distinto cada vez. |
| **Uno distinto en cada vuelta** | El primer elemento en la primera vuelta del runner, el segundo en la segunda, y así. Cuando ejecutas varios casos a mano, uno distinto para cada caso. |
| **El que cumpla…** | El primer elemento que cumple una condición. Elige el **Campo**, la **Condición** (**es**, **no es**, **contiene**, **es mayor que**, **es menor que**) y el **Valor**. |
| **Todos** | Toda la lista. Solo cuando los pasos siguientes pueden recibir varios elementos. |

La regla se guarda en el paso del archivo Arazzo, bajo la extensión `x-luvin-pick`. Las demás herramientas de Arazzo la ignoran.

```yaml title="shop.arazzo.yaml" {3-8}
- stepId: getCustomer
  operationId: getCustomer
  x-luvin-pick:
    "#/activeCreditCards":
      rule: match
      field: bank
      op: eq
      value: Banco Sur
```

Con una regla guardada, el diálogo ya no aparece para esa lista, ni en tus ejecuciones ni en el runner. El runner de workflows muestra las listas y sus reglas en **Listas en las respuestas**. Para borrar una regla, pulsa **Quitar** junto a ella. Mira [Ejecuta workflows](/es/runner/workflows/#listas-en-las-respuestas).

### Cuando «El que cumpla…» no encuentra nada

Si ningún elemento cumple la condición:

- En el runner, y en una prueba de rendimiento, el paso falla con *Ningún elemento de la lista (3) cumple la regla: bank es Banco Sur.* La ejecución no sigue con otro elemento como si nada.
- Cuando ejecutas a mano, el diálogo te pregunta, como si no hubiera regla.

## Qué queda registrado

El paso que devolvió la lista guarda una nota, **Elegido al ejecutar**. Por ejemplo: *De la lista abilities se siguió con «lightning-rod» (elemento 2 de 2).* Debajo, la nota dice qué valor recibió cada parámetro.

## Cuándo no aparece el diálogo

- Si la lista tiene un solo elemento, en **Simulación**. La ejecución sigue con ese, y el paso guarda una nota: *De la lista: La lista types trajo un solo elemento («…»): se usó ese.* Contra la **API real** el diálogo sí aparece, para que confirmes lo que devolvió el servicio.
- Si el paso tiene una regla guardada para esa lista. Mira [Reglas para las próximas veces](#reglas-para-las-próximas-veces).
- En el [runner](/es/runner/workflows/). Nunca se detiene a preguntar: usa la regla guardada o el elemento que dice el diseño.
- Al probar una ruta, con **▷ Probar** en el lienzo. Igual que el runner, usa la regla guardada o el elemento que dice el diseño. Mira [Probar rutas y cobertura](/es/test/probe-routes/).
- Si la lista llega vacía.
- Si ningún paso posterior usa datos de la lista.
- Si el paso que devuelve la lista falló.

Cuando ejecutas solo un paso, hasta un paso o desde un paso, el diálogo sí aparece, como en una ejecución normal. Mira [Depurar un workflow](/es/test/debug/#ejecuta-solo-hasta-o-desde-un-paso).

**Detener ejecución**, en el diálogo, cancela la ejecución.
