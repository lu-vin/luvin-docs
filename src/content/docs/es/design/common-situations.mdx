Esta página responde «¿cómo hago…?» para las situaciones más comunes al diseñar un workflow. Cada una tiene la situación en una línea, cómo se hace en la pestaña **Diseño**, qué escribe Luvin en el archivo Arazzo y la página que la explica completa.

Los ejemplos usan el ejemplo de la Pokédex de la app y una tienda genérica: iniciar sesión, listar productos, crear un pedido y volver a leerlo.

<Aside type="tip" title="Lienzo o YAML">
Casi todo se hace en el lienzo. Unas pocas cosas, como los criterios sobre el body o las rutas de falla sobre un campo de la respuesta, se escriben en la [pestaña YAML](/es/design/arazzo-editor/). Cada situación dice cuál. Lo que escribes a mano se conserva al volver al lienzo, y **\{ \} YAML** muestra el archivo al lado del lienzo mientras trabajas.
</Aside>

## Pasar datos de un paso al siguiente

### El token del login va a los pasos siguientes

El login devuelve `accessToken`, y las llamadas siguientes lo necesitan como autorización.

Cuando Luvin reconoce el token en la respuesta del login, o en el script de un request de Postman o Bruno, lo conecta a medida que agregas los pasos. Un aviso dice cuántos pasos lo usan, con **Deshacer**. Si no, haz clic en el paso del login y, en **Entrega**, elige el campo que se usa como autorización en los pasos siguientes.

La tarjeta del login muestra **🔑 inicia sesión**, y cada paso que usa el token muestra **🔑**. El header está en la pestaña **Autorización** de cada paso, no en **Headers**.

```yaml
- stepId: login
  outputs:
    token: $response.body#/accessToken
- stepId: createOrder
  parameters:
    - name: Authorization
      in: header
      value: Bearer {$steps.login.outputs.token}
```

El patrón **Iniciar sesión y usar el token** de **＋ Paso** hace lo mismo de una vez. Detalle: [Pasa el token del login a los pasos siguientes](/es/authorization/token-from-login/).

### Un id de una respuesta va en la ruta del paso siguiente

Agregas `GET /pokemon-species/{idOrName}` después de `GET /pokemon/{idOrName}`, y el segundo necesita el `id` del primero.

<Steps>
1. Agrega las dos operaciones con **＋ Paso**.
2. Mira la segunda tarjeta. Su `idOrName` muestra el chip **← id · de 1**, con una `?` delante: Luvin lo conectó por ti y agregó el output `id` al primer paso.
3. Si el origen no es el que quieres, haz clic en el paso y, en su pestaña **Datos**, elige otro en la lista **Origen**.
</Steps>

Haz clic en la segunda tarjeta para ver la línea de datos que va del output `id` del paso 1 a `idOrName`.

![Un workflow nuevo con dos pasos: Inicio tiene el input idOrName, el primer paso lo lee y entrega id, y el segundo muestra el chip ← id · de 1](/media/es/design-auto-wired.webp)

<video controls muted playsinline preload="metadata" poster="/media/es/design-wire.webp" src="/media/es/design-wire.mp4"></video>

```yaml
- stepId: getPokemonSpecies
  parameters:
    - name: idOrName
      in: path
      value: $steps.getPokemon.outputs.id
```

La `?` significa que Luvin está menos seguro: revísala. Detalle: [Conectar datos entre pasos](/es/design/wire-data/).

### Un valor que nadie entrega se vuelve un input

Cuando ningún paso anterior devuelve un valor que el paso necesita, Luvin crea un input del workflow con el nombre del valor. En la imagen de arriba, **Inicio** tiene `idOrName`, creado al agregar el primer paso.

Para hacerlo tú, abre la lista **Origen** del valor y elige **Nuevo input «nombre»**. El input se crea como obligatorio.

```yaml
inputs:
  type: object
  required: [idOrName]
  properties:
    idOrName: { type: string }
steps:
  - stepId: getPokemon
    parameters:
      - { name: idOrName, in: path, value: $inputs.idOrName }
```

Los inputs se llenan en la pestaña **Inputs**. Lee [Inputs](/es/test/inputs/).

### Un valor fijo se vuelve un input, y al revés

Un paso envía siempre `currency: EUR`. Quieres casos que prueben otras monedas.

<Steps>
1. En la tarjeta, apunta al valor fijo. Junto a él aparece **→ input**.
2. Haz clic en **→ input**. **Inicio** recibe el input `currency`, con `EUR` como valor, y el paso lo lee.
3. Para elegir varios a la vez, haz clic en **+ Volver input otro valor fijo** en **Inicio** (o **Elegir datos variables…** cuando todavía no hay inputs), marca los valores en **Datos para variar por caso** y haz clic en **Convertir en inputs**.
</Steps>

![La tarjeta de createOrder con el botón → input junto al valor fijo de currency](/media/es/design-promote-one.webp)

![El diálogo Datos para variar por caso con dos valores marcados: currency y address/city](/media/es/design-pick-data.webp)

Para volver atrás no hay un solo botón. Hazlo en dos movimientos:

<Steps>
1. Haz clic en el paso y, en la lista **Origen** del valor, elige **Valor fijo…**. Escribe el valor.
2. Haz clic en **Inicio** y borra el input con su papelera.
</Steps>

Si borras un input que un paso todavía usa, aparece la barra **A este workflow le faltan datos**. Justo después de volver inputs unos valores, **↶ Deshacer** también devuelve los valores fijos.

<video controls muted playsinline preload="metadata" poster="/media/es/design-promote.webp" src="/media/es/design-promote.mp4"></video>

```yaml
inputs:
  properties:
    currency:
      type: string
      description: createOrder · body · currency
      example: EUR
steps:
  - stepId: createOrder
    requestBody:
      payload:
        currency: $inputs.currency
```

Detalle: [Parámetros y body](/es/design/parameters-and-body/#convertir-un-valor-fijo-en-input).

### Un campo que viene de una lista

`listProducts` devuelve `items`, una lista, y el paso siguiente necesita el `sku` de un producto.

<Steps>
1. Haz clic en el paso siguiente y abre la lista **Origen** del valor.
2. Debajo de `listProducts`, elige **items/sku (de una lista: eliges cuál al ejecutar)**.
</Steps>

El campo se muestra sin su posición: `items/sku`. En el archivo Luvin escribe la primera posición, y cuando ejecutas un caso se detiene después del paso y pregunta con qué elemento seguir. Los outputs del paso también dejan exponer la **lista completa**.

![Los outputs de listProducts: la nota sobre la lista, la etiqueta lista completa e items/sku marcado](/media/es/design-list-outputs.webp)

```yaml
- stepId: listProducts
  outputs:
    sku: $response.body#/items/0/sku
```

Detalle: [Outputs](/es/design/outputs/#campos-que-son-listas) y [Elige un elemento de una lista](/es/test/lists/).

### Objetos anidados y listas en un body

El pedido tiene un objeto `address` y una lista de `lines`.

<Steps>
1. Haz clic en el paso. En la pestaña **Datos**, bajo **Body**, los campos dentro de objetos aparecen con su ruta: `address/city`, `address/zip`. Dale un origen a cada uno.
2. Para la lista, haz clic en **Editar como JSON**, escribe los elementos y haz clic en **Aplicar**. Usa `"$inputs.nombre"` o `"$steps.paso.outputs.valor"` como valores.
</Steps>

![El cuadro Editar como JSON de createOrder con el objeto address y la lista lines](/media/es/design-body-json.webp)

```yaml
requestBody:
  contentType: application/json
  payload:
    customer: Ana
    address: { city: Madrid, zip: '28001' }
    lines:
      - { sku: $steps.listProducts.outputs.sku, qty: 1 }
```

Detalle: [Parámetros y body](/es/design/parameters-and-body/#editar-el-body-como-json).

### La misma operación dos veces en un workflow

Quieres consultar un Pokémon y, más adelante, otro. Agrega otra vez la misma operación con **＋ Paso**, o elige el paso y presiona **⌘D** para duplicarlo. El paso nuevo recibe otro id: `getPokemon2` si lo agregas, `getPokemon_2` si lo duplicas. Cada paso tiene sus propios parámetros y outputs, así que los pasos siguientes pueden leer cualquiera de los dos.

```yaml
- stepId: getPokemon
  operationId: $sourceDescriptions.pokeapi.getPokemon
- stepId: getPokemon2
  operationId: $sourceDescriptions.pokeapi.getPokemon
```

Para darle un título o un id más claros, haz clic en el paso y cámbialos arriba en su panel. Detalle: [Organizar un workflow](/es/design/organize/).

## Cambiar el orden o deshacer

### Reordenar, quitar, deshacer y rehacer

<Steps>
1. Arrastra una tarjeta por encima o por debajo de otra, o elígela y presiona **⌥↑** o **⌥↓**.
2. Si el paso ahora se ejecuta antes del que le da datos, la barra **Revisa el orden:** lo avisa. Haz clic en **Deshacer** en la barra.
3. Para quitar un paso, haz clic en **×** en su tarjeta, o elígelo y presiona **⌫**. Una ventana lista lo que se rompe; haz clic en **Quitar el paso**.
4. **↶ Deshacer** y **↷ Rehacer** sobre el lienzo (⌘ + Z y ⇧ + ⌘ + Z) recorren tus cambios.
</Steps>

![La barra Revisa el orden: getOrder usa datos de createOrder, que ahora se ejecuta después](/media/es/design-order-warning.webp)

<video controls muted playsinline preload="metadata" poster="/media/es/design-organize.webp" src="/media/es/design-organize.mp4"></video>

Detalle: [Organizar un workflow](/es/design/organize/).

### Copiar pasos a otro workflow, o volverlos un workflow propio

<Steps>
1. Haz Shift + clic en los pasos. Una barra dice **3 pasos elegidos**.
2. Para copiarlos, presiona **⌘C**, abre el otro workflow, elige un paso y presiona **⌘V**. Los ids que ya existen reciben `_2`.
3. Para reutilizarlos, haz clic en **⇪ Extraer a un workflow** (solo pasos seguidos), dale un nombre, revisa la vista previa y haz clic en **Extraer**.
</Steps>

## Decidir qué cuenta como éxito

### Éxito por status

Haz clic en el paso, abre la pestaña **Éxito y rutas** y, en **Es éxito si**, elige el status que esperas después de `$statusCode ==`. Luvin escribe `$statusCode == 201`.

### Éxito por una condición sobre la respuesta

El lienzo edita el status. Las condiciones sobre el body o los headers se escriben en la pestaña YAML, dentro de `successCriteria`. Se tienen que cumplir todos los criterios. La tarjeta y el panel los listan con su tipo, y el panel ofrece **Editar en el YAML**.

| Tipo | Ejemplo |
|---|---|
| Simple | `- condition: $response.body#/capture_rate >= 0` |
| Regex | `- context: $response.header.Content-Type`<br />`  condition: ^application/json`<br />`  type: regex` |
| JSONPath | `- context: $response.body`<br />`  condition: $.abilities[?(@.is_hidden == false)]`<br />`  type: jsonpath` |
| XPath (respuestas XML) | `- context: $response.body`<br />`  condition: /order/status`<br />`  type: xpath` |

Un JSONPath escrito como comparación, como `$.legendary == true`, no se cumple nunca. **⚠ por revisar** lo marca y ofrece **Cambiarla**, que lo reescribe como `$response.body#/legendary == true`. Lee [Por revisar](/es/design/review/).

![La pestaña Éxito y rutas de getSpecies: el status después de $statusCode == y un criterio extra con su tipo y Editar en el YAML](/media/es/design-criteria-panel.webp)

Detalle: [Éxito y errores](/es/design/success-and-errors/), [Criterios de éxito](/es/reference/criteria/) y la receta [Comprueba más que el status](/es/recipes/criteria/).

## Decidir qué pasa después de un paso

Cada paso puede tener rutas: qué hacer si falla, y adónde ir si pasa y se cumple una condición. Son filas de la tarjeta, en rojo (**Si falla**) y en verde (**Si pasa y se cumple**), con una flecha a la izquierda hacia donde van.

<video controls muted playsinline preload="metadata" poster="/media/es/design-errors.webp" src="/media/es/design-errors.mp4"></video>

### Un error esperado termina el workflow

«El Pokémon no existe» es un resultado conocido, no una caída.

<Steps>
1. En la tarjeta, busca la fila roja **404 · sin ruta** y haz clic en **Elegir qué hacer**. O haz clic en **＋ Qué hacer si falla** y escribe `404`.
2. Haz clic en **Terminar el workflow**, revisa la vista previa y haz clic en **Agregar**.
</Steps>

La flecha de la ruta va a **Fin del workflow**.

```yaml
onFailure:
  - name: on404
    type: end
    criteria:
      - condition: $statusCode == 404
```

Luvin también genera un caso que simula el 404 y comprueba que la ruta se toma. Ejemplo que se puede ejecutar: [Espera un error](/es/recipes/expected-error/).

### Reintentar con espera y límite

En el editor de rutas, elige **Reintentar**. Empieza con una espera de 2 segundos y hasta 3 veces; cambia los dos números antes de hacer clic en **Agregar**. En el panel, un status sin ruta también tiene **Reintenta**, que escribe lo mismo con un clic. Luvin nunca espera más de 10 segundos entre dos intentos contra la API real.

```yaml
onFailure:
  - name: retry429
    type: retry
    retryAfter: 2
    retryLimit: 3
    criteria:
      - condition: $statusCode == 429
```

Para volver a iniciar sesión antes del reintento, elige **Renovar y reintentar** y el workflow del login. Lee [Agregar o cambiar una ruta](/es/design/branch-menu/).

### Ir a otro paso

Elige **Ir a otro paso** y el paso en **Ir al paso**. En la tarjeta, una flecha roja punteada va de la fila a ese paso. Una ruta que vuelve hacia atrás muestra el límite del runner: **(el runner corta a las 200 ejecuciones)**.

![El lienzo: la fila 409 de createOrder va a listProducts, con una flecha roja punteada a la izquierda de las tarjetas](/media/es/design-jump-line.webp)

```yaml
onFailure:
  - name: on409
    type: goto
    stepId: listProducts
    criteria:
      - condition: $statusCode == 409
```

Para llevar un error a un paso que todavía no existe, elige **o un paso nuevo…**. Lee [Un paso nuevo para una ruta](/es/design/branch-new-step/).

### Seguir en otro workflow

Elige **Seguir en otro workflow** y el workflow, de este archivo o de otro archivo Arazzo de la colección. La flecha termina en un recuadro debajo de **Fin del workflow**: **↗ Sigue en «…»**. El control no vuelve.

```yaml
onFailure:
  - name: on500
    type: goto
    workflowId: reportProblem
    criteria:
      - condition: $statusCode == 500
```

Para un workflow de otro archivo Arazzo, Luvin agrega ese archivo a las fuentes y escribe `$sourceDescriptions.<fuente>.<workflowId>`.

### Desviar cuando el paso pasa y se cumple una condición

La especie es legendaria y quieres saltar a otro paso. `getSpecies` tiene el output `isLegendary`, que lee `$response.body#/is_legendary`.

<Steps>
1. En la tarjeta de `getSpecies`, haz clic en **＋ Desviar si pasa y se cumple una condición**.
2. En **Si el dato**, elige el output `isLegendary` y escribe `true` después de **es**.
3. Elige **Ir a otro paso**, **Seguir en otro workflow** o **Terminar con éxito**, y haz clic en **Agregar**.
</Steps>

```yaml
onSuccess:
  - name: ifIs_legendary
    type: goto
    stepId: getLegend
    criteria:
      - condition: $response.body#/is_legendary == true
```

Si un desvío salta un paso cuyos datos usa un paso posterior, **⚠ por revisar** te avisa. Ejemplo que se puede ejecutar: [Reintenta, salta y termina ante errores](/es/recipes/error-branches/).

### Una regla para todos los pasos

Un 429 puede pasar en cualquier paso. En lugar de una ruta en cada uno, haz clic en **Inicio** y, en **Si falla cualquier paso**, haz clic en **＋ Regla para todos los pasos**. Cada tarjeta lo recuerda: **Si nada de esto aplica, usa las reglas de Inicio (429)**.

```yaml
failureActions:
  - name: retry429
    type: retry
    retryAfter: 2
    retryLimit: 3
    criteria:
      - condition: $statusCode == 429
```

Detalle: [El panel Rutas y las reglas para todos los pasos](/es/design/routes-panel/).

### Ordenar y revisar las rutas

La pestaña **Éxito y rutas** de un paso lista sus rutas en orden: gana la primera que se cumple. Usa **↑** y **↓** para reordenar, **✎** para cambiar y **✕** para quitar. El chip **⚠ por revisar** lista las rutas que saltan datos, van a un paso que ya no está, repiten sin límite o no se cumplen nunca. Lee [Por revisar](/es/design/review/).

## Repetir un paso o esperar

### Recorrer todas las páginas

Haz clic en **＋ Paso**, luego en **Recorrer todas las páginas**, en **Patrones · Arazzo estándar**, y después en la operación. El paso se repite mientras la respuesta tenga una página siguiente, y manda el cursor de la vuelta anterior.

```yaml
onSuccess:
  - name: siguientePagina
    type: goto
    stepId: listProducts
    criteria:
      - condition: $response.body#/nextCursor != null
```

Las APIs que paginan con `skip` y `limit` no se pueden recorrer así en Arazzo. Detalle: [Patrones de Arazzo estándar](/es/design/patterns/).

### Esperar a que termine un trabajo

Elige **Esperar hasta que termine** y la operación que consulta el trabajo. El paso pasa cuando `status` dice `done`, o cuando un campo como `completed` es `true`, y reintenta cada 2 segundos, hasta 10 veces, mientras no.

```yaml
successCriteria:
  - condition: $statusCode == 200
  - condition: $response.body#/completed == true
onFailure:
  - name: mientrasPendiente
    type: retry
    retryAfter: 2
    retryLimit: 10
    criteria:
      - condition: $response.body#/completed == false
```

Detalle: [Patrones de Arazzo estándar](/es/design/patterns/#esperar-hasta-que-termine).

## Usar otros workflows

### Depender de otro workflow del mismo archivo o de otro archivo

`placeOrder` necesita el token que devuelve el workflow `login`, y `login` está en `auth.arazzo.yaml`.

<Steps>
1. Haz clic en **Inicio**. En **Depende de**, abre **Agregar un workflow…**.
2. Elige un workflow en **De este archivo** o en el grupo de otro archivo, como **De auth.arazzo.yaml**.
3. Arriba de **Inicio** aparece la tarjeta **⇡ Depende de** con los outputs de ese workflow. Úsalos desde la lista **Origen** de cualquier valor, o arrastra su punto.
</Steps>

![La lista Agregar un workflow con los grupos De este archivo y De auth.arazzo.yaml](/media/es/design-depends-options.webp)

![La tarjeta Depende de sobre Inicio: el workflow login de auth.arazzo.yaml y su output token](/media/es/design-depends-card.webp)

```yaml
sourceDescriptions:
  - { name: auth, url: ./auth.arazzo.yaml, type: arazzo }
workflows:
  - workflowId: placeOrder
    dependsOn: [$sourceDescriptions.auth.login]
```

Para un workflow del mismo archivo, `dependsOn` tiene solo su id: `dependsOn: [browseProducts]`. Detalle: [Workflows que usan otros workflows](/es/design/dependencies/).

### Llamar a un workflow como un paso

Haz clic en **＋ Paso** y elige el workflow en **Workflows de este Arazzo** (o **De otros archivos Arazzo**). El paso nuevo lista los inputs de ese workflow en **Inputs del workflow**, conectados como cualquier otro valor, y sus outputs. En la tarjeta, **▸ Ver sus N pasos** lista los pasos que ejecuta.

![El panel de un paso que llama al workflow browseProducts: su input limit y sus outputs sku y price](/media/es/design-call-workflow.webp)

<video controls muted playsinline preload="metadata" poster="/media/es/design-depends.webp" src="/media/es/design-depends.mp4"></video>

```yaml
- stepId: browseProducts
  workflowId: browseProducts
  parameters:
    - { name: limit, value: $inputs.limit }
  outputs:
    sku: $outputs.sku
    price: $outputs.price
```

## Definir una vez, usar en varios pasos

### Rutas de falla y parámetros reutilizables

<Steps>
1. Dale a un paso una ruta de falla por un status, por ejemplo **Reintentar** con **429**, o dale un valor a un parámetro.
2. Guárdalo: **Guardar como reutilizable** bajo la ruta en la pestaña **Éxito y rutas**, o ♻ en el parámetro en la pestaña **Datos**. Escribe un nombre y guarda.
3. Aplícalo a otro paso: arrástralo desde **Reutilizables**, en el panel de **Inicio**, hasta la tarjeta, o elígelo en **O aplica un reutilizable:** en el editor de rutas.
4. Haz clic en él en **Inicio** para editarlo una vez para todos los pasos. **Se usa en** lista los pasos.
</Steps>

![El panel del reutilizable unauthorized de PayPal: termina el workflow ante un 401 y se usa en cinco pasos](/media/es/design-reusable-panel.webp)

<video controls muted playsinline preload="metadata" poster="/media/es/design-reusables.webp" src="/media/es/design-reusables.mp4"></video>

```yaml
components:
  failureActions:
    tooManyRequests:
      name: tooManyRequests
      type: retry
      retryAfter: 1
      retryLimit: 3
      criteria:
        - condition: $statusCode == 429
# en cada paso:
onFailure:
  - reference: $components.failureActions.tooManyRequests
```

En la tarjeta, una ruta reutilizable lleva la marca ♻. Detalle: [Reutilizables](/es/design/reusables/).

## Mensajes y eventos

### Enviar y recibir mensajes

<Aside type="caution">
Los pasos de mensajería siempre se simulan. Luvin no se conecta a brokers (Kafka, AMQP, MQTT…): el paso usa los ejemplos del contrato AsyncAPI, también cuando ejecutas contra la API real.
</Aside>

Agrega la operación de AsyncAPI con **＋ Paso**, como cualquier operación: lleva la etiqueta **SEND** o **RECEIVE**. Luvin escribe `action`, el id de correlación y, para una recepción, `timeout: 5000`. Los outputs se editan en el panel. Los criterios sobre el mensaje, como el de abajo, y las rutas de falla se escriben en la pestaña YAML. Lee [Agrega un paso de mensajería](/es/design/messaging/#agrega-un-paso-de-mensajería).

![El panel de awaitConfirmation, un paso de recepción, con su criterio sobre el mensaje y su output entryNumber](/media/es/design-messaging-receive.webp)

```yaml
- stepId: awaitConfirmation
  channelPath: '{$sourceDescriptions.pokedexEvents.url}#/channels/sightingConfirmed'
  action: receive
  correlationId: $inputs.correlationId
  timeout: 5000
  successCriteria:
    - condition: $message.payload#/status == 'CONFIRMED'
```

Detalle: [Pasos de mensajería](/es/design/messaging/).

## Sin contrato

### Armar desde requests guardados

<Steps>
1. Crea un workflow con **+** › **Nuevo Arazzo**.
2. En el lienzo vacío, haz clic en **Armar con requests de la colección** y haz clic en tus requests en orden. También puedes arrastrarlos desde el árbol de la barra lateral.
3. Haz clic en un paso y en **Probar este paso**, o ejecuta el workflow una vez contra la API real, para que Luvin aprenda las respuestas.
4. La barra **Luvin encontró 1 conexión(es) entre pasos** propone las conexiones. Haz clic en **Conectar**.
</Steps>

### Marcar los campos obligatorios de un request

Un request no dice qué campos exige la API. Su tarjeta muestra **obligatorios sin marcar**, y una barra sobre el lienzo dice cuántos pasos no tienen la respuesta, con **Marcar**. Haz clic en **Marcar**, marca los campos obligatorios y haz clic en **Guardar**. Para cambiarlo después, haz clic en el paso y luego en **Campos obligatorios (n)**, arriba en su panel.

![El diálogo ¿Qué exige la API en «Crear pedido»? con customer marcado como obligatorio](/media/es/design-required-fields.webp)

```yaml title="requests/create-order.request.yaml"
requiredFields:
  - body:customer
```

Detalle: [Marca los campos obligatorios de un request](/es/design/required-fields/).

## Arreglar un workflow

### Completar los datos que faltan

Después de que cambia un contrato, o de que editas el YAML, un paso puede usar un input que el workflow no declara, o no enviar algo que el contrato exige. La barra **A este workflow le faltan datos** dice qué. Haz clic en **Completar**. **↶ Deshacer** lo revierte.

![La barra A este workflow le faltan datos: usa inputs que el workflow no declara, username, con el botón Completar](/media/es/design-gaps-bar.webp)

Detalle: [Completa los datos que faltan](/es/design/complete-gaps/).

### Editar el YAML a mano

<Steps>
1. Abre la pestaña **YAML**, o **\{ \} YAML** › **Editar en YAML**. Es el mismo archivo que edita el lienzo.
2. Escribe. Después de `$`, `$steps.` o `$inputs.`, el editor sugiere lo que existe.
3. Revisa la marca sobre el texto y la lista **Problemas** debajo.
4. Vuelve a **Diseño**. Lo que escribiste se queda, también después de cambiar otras cosas en el lienzo.
</Steps>
