## The key lines

```yaml title="criteria.arazzo.yaml" {30-37}
arazzo: 1.0.1
info:
  title: Success criteria beyond the status
  version: 1.0.0
sourceDescriptions:
  - name: dummyjson
    url: ./dummyjson.openapi.yaml
    type: openapi
workflows:
  - workflowId: searchPhones
    summary: Search products and check the status, a number, a header and a price
    inputs:
      type: object
      properties:
        q: { type: string, example: phone }
    steps:
      - stepId: search
        operationId: searchProducts
        parameters:
          - name: q
            in: query
            value: $inputs.q
          - name: limit
            in: query
            value: 3
          - name: select
            in: query
            value: title,price
        successCriteria:
          - condition: $statusCode == 200
          - condition: $response.body#/total > 0
          - context: $response.header.Content-Type
            condition: ^application/json
            type: regex
          - context: $response.body
            condition: $.products[?(@.price > 0)]
            type: jsonpath
        outputs:
          total: $response.body#/total
          firstTitle: $response.body#/products/0/title
    outputs:
      total: $steps.search.outputs.total

  - workflowId: impossiblePrice
    summary: Fails on purpose - no phone costs more than 100000
    steps:
      - stepId: search
        operationId: searchProducts
        parameters:
          - name: q
            in: query
            value: phone
          - name: limit
            in: query
            value: 3
          - name: select
            in: query
            value: title,price
        successCriteria:
          - condition: $statusCode == 200
          - context: $response.body
            condition: $.products[?(@.price > 100000)]
            type: jsonpath
```

| Line | What it does |
|---|---|
| 30 | A simple condition on the status. Simple is the default type. |
| 31 | A simple condition on a value of the body: the search found at least one product. |
| 32-34 | A `regex` criterion. Its `context` is the header `Content-Type`, which must start with `application/json`. |
| 35-37 | A `jsonpath` criterion on the whole body. It passes when the path finds at least one match: here, a product with a price above 0. |
| 44-60 | The second workflow, `impossiblePrice`, asks for a price above 100000. No phone costs that much, so it fails on purpose. |

## On the canvas

Open `searchPhones` in the **Design** tab. The card of `search` lists the four criteria under **Success criteria**, each with its type on the right: **simple**, **simple**, **regex** and **jsonpath**. A criterion with a `context` shows it first, as in `$response.header.Content-Type ~ ^application/json`.

In the panel of the step, the tab **Success and routes** has them under **It succeeds if** · **all are met**. The status is a list you change there; the other three are edited in the YAML tab, with **Edit in the YAML**.

## What you get

Both workflows call `GET /products/search?q=phone&limit=3&select=title,price`.

| Workflow | Step | HTTP status | Result |
|---|---|---|---|
| `searchPhones` | `search` | 200 | All four criteria hold. Output `total` = `23`. **Passed**. |
| `impossiblePrice` | `search` | 200 | The API answered 200, but the JSONPath criterion does not hold. **Failed**. |

The reason Luvin prints for `impossiblePrice` is:

```text
JSONPath found no matches in $response.body.
```

A status of 200 is not enough: the step fails because a criterion fails. The workflow stops there and its outputs stay empty. In `expect.json` of the recipe this workflow is marked `failed`, because failing is what it should do.

A criterion of type `regex` explains itself too. With `condition: ^text/html` on the same header, the reason reads:

```text
$response.header.Content-Type = "application/json; charset=utf-8" does not match /^text/html/
```

## Try this

- Change `q` to `laptop` in the **Inputs** tab and run `searchPhones` again. The total becomes `5` and the criteria still hold.
- In `impossiblePrice`, change `100000` to `100`. The criterion now finds the products that cost more than 100 and the workflow passes.

## A JSONPath that is really a comparison

A JSONPath criterion finds things; it does not compare. Suppose you write the total check as JSONPath:

```yaml
- context: $response.body
  condition: $.total > 0
  type: jsonpath
```

`$.total > 0` is not a JSONPath query, so it never finds anything and `search` would always fail. Luvin catches it before you run: the toolbar shows **⚠ 1 to review**, and the warning reads **Step 1: the criterion «$.total > 0» is not valid JSONPath and is never met: the step always fails.** with **Write it as a simple condition: «$response.body#/total > 0». Any Arazzo tool evaluates it that way.**

Click the warning, then **Change it** in the **Success and routes** tab. Luvin rewrites that criterion as `condition: $response.body#/total > 0`, the simple condition of line 31. The filters of this recipe, such as `$.products[?(@.price > 0)]`, are valid queries and are not flagged. See [To review](/design/review/#a-jsonpath-condition-that-never-holds).
