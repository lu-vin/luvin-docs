When you import a collection from Postman or Bruno, its environments come with it. Each one becomes a Luvin environment of the new collection, with its variables and secrets. Your requests keep their `{{baseUrl}}` and work as they did.

## Example: the shop from Postman

You exported from Postman the collection **Shop API** and two environments, **Shop local** and **Shop staging**. Each environment has `baseUrl`, `clientId` and a secret `apiKey`.

<Steps>

1. Click **+** in the tabs (**Create or import**), then **Import from Postman or Bruno**.
2. Under Postman, click **Choose .json files** and select the three files together: the collection and the two environments.
3. Read the summary. It says **2** environments and lists them with how many variables each has: *Environments: Shop local (3) · Shop staging (3)*.
4. Click **Import (N requests)**.

</Steps>

The new collection has the environments `Shop local` and `Shop staging`, in `environments/shop-local.yaml` and `environments/shop-staging.yaml`. Open **Get customer**, which sends `GET {{baseUrl}}/customers/42`, and send it: `baseUrl` comes from the active environment, as in Postman.

![The Import from Postman or Bruno dialog with a card for Postman and a card for Bruno](/media/en/import-postman.webp)

## What to choose

<Tabs>
<TabItem label="Postman">

Click **Choose .json files** and pick the exported collection (v2.0 or v2.1) together with its environment files. You can also drop them all on the dialog. A globals file exported from Postman becomes a [global environment](/environments/variable-levels/) of the workspace, not an environment of the collection.

If you choose several collections at once, each of them gets every environment you chose.

</TabItem>
<TabItem label="Bruno">

Click **Choose folder** and pick the collection folder, as Bruno keeps it in git. Each file of its `environments/` folder, such as `environments/staging.bru`, becomes an environment named like the file: `staging`.

Or click **Choose .json** and pick the file Bruno exports. Its environments come inside it.

</TabItem>
</Tabs>

## What each variable becomes

| In Postman or Bruno | In Luvin |
|---|---|
| An enabled variable | A variable with its value. |
| A Postman variable of type secret | A secret, with its value. The value is stored encrypted on this computer, not in the file. |
| A Bruno secret (`vars:secret`) | A secret with an empty value. Bruno does not save secret values, so type them again. |
| A disabled variable | Not imported. |
| A variable with a name Luvin does not accept, such as `my var` | Not imported. The summary says *The variable “my var” has an invalid name and was skipped.* |
| The same name twice in one environment | The first one is kept. |
| A collection variable (Postman `variable`, Bruno `vars:pre-request` of the collection) | A [collection variable](/environments/variable-levels/): the same in all the collection's environments. |
| A Postman collection variable of type secret | A secret in every environment that does not define it, because a collection variable cannot be secret. The summary says so. If no environment came with the collection, Luvin creates one called `local` for them. |
| A variable of a Postman globals file | A variable of the workspace global environment with that file's name. If one with that name exists, only the variables it lacks are added: no value is overwritten. |
| A Bruno request's `vars:pre-request` | A [variable of that request](/environments/variable-levels/): it only applies there. |

The summary lists where the variables go, for example *1 collection variable(s): they apply in all its environments*. Collections you imported before keep their variables where they were.

A variable named `baseUrl` stays a variable, not a [base URL](/environments/base-urls/). It works the same in `{{baseUrl}}/customers`. Imported environments have no color: give them one if you want. See [Create, rename, color and delete](/environments/manage/).

<Aside type="note" title="Dynamic variables come along">
Requests that use `{{$guid}}`, `{{$randomEmail}}` or another Postman dynamic variable keep working, because Luvin uses the same names. A `$` name Luvin does not have shows in red. See [Postman-compatible variables](/environments/postman-variables/).
</Aside>

## After the import

<Steps>

1. Open the **Environments** panel. The first imported environment is active.
2. Open each environment and check **Secrets**. Fill in any empty value, as Bruno secrets always are.
3. Open a request and check that no `{{name}}` is red. A red one was skipped or never existed in that environment.
4. If you add a contract and workflows later, fill in the **Credentials** their security schemes ask for. See [Credentials](/environments/credentials/).

</Steps>

Postman and Bruno scripts come with the collection and run once you trust it. When a script sets a variable, such as `pm.environment.set("token", …)`, it changes the **current value** of that variable on this computer. The environment file does not change. See [Variables a script saves](/requests/scripts/#variables-a-script-saves).

## Things to know

- An import creates a new collection, or replaces the content of one with the same name, environments included. See [When the collection already exists](/get-started/import/#when-the-collection-already-exists). To add only a Postman environment to a collection you already have, create the environment in Luvin and copy the values.
- If you choose only environment files, Luvin says **Those are only environments: choose the collection too.**
- You need a workspace open to import. See [Create and open a workspace](/workspaces/create-and-open/).
