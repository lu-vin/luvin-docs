A contract says in its `securitySchemes` how its API is protected: an API key in a header, a Bearer token, a user and password. The **Credentials** section of the environment asks you for one value per scheme, so each environment can use its own key or token.

## Example: the shop and the PayPal sandbox

The shop contract protects its operations with two schemes, `shopKey` (an API key in the header `X-Shop-Key`) and `shopBearer` (a Bearer token). Open the environment `staging`:

| Field | Type shown | Hint |
|---|---|---|
| `shopKey` | `apiKey · header "X-Shop-Key"` | *API key · source shop* |
| `shopBearer` | `bearer` | *Bearer token (sent as Authorization: Bearer …) · source shop* |

The badge of the section says **0/2 filled**, in amber. Paste the key in `shopKey` and write `{{shopToken}}` in `shopBearer`, a secret you already have. The badge turns green: **2/2 filled**. A protected step now goes out with `X-Shop-Key: <your key>` and `Authorization: Bearer <the value of shopToken>`.

The PayPal example works differently. Its environment `Sandbox` shows one credential, `oauth2`, at **0/1 filled**, and that is fine: the PayPal workflows get their token from the **Authorization** tab of the workflow, which uses `{{clientId}}` and `{{clientSecret}}`. A credential is only needed when nothing else authorizes the call.

## Which credentials are listed

Luvin lists the security schemes of the operations your workflows call. A scheme that no step uses does not appear.

| Detail | What you see |
|---|---|
| One field per contract and scheme | The label is the scheme name, such as `shopKey`. When two contracts use the same scheme name, the label starts with the source: `shop · shopKey`. |
| The type | `bearer`, `basic`, `apiKey`, `oauth2` or `openIdConnect`. An API key also shows where it goes and its name: `apiKey · header "X-Shop-Key"`. |
| The hint | What to paste, and the source it belongs to. |
| An operation with several alternatives | Luvin uses the first one that is not empty. |
| No scheme at all | *The contracts do not declare `securitySchemes`. If authentication goes in headers or in a workflow step, it is taken from the inputs.* |

Any other type, such as `mutualTLS`, says *Unsupported security type; it will be ignored*.

## Fill in a credential

<Steps>

1. Open the environment: click the left half of the pill at the top right (the collection environment) and choose **Configure environment…**.
2. In **Credentials**, find the scheme.
3. Paste the value, or write a secret such as `{{apiKey}}`. The placeholder reminds you: *Paste the value or use a secret: `{{apiKey}}`*.
4. Check the badge, for example **1/2 filled**. It is amber while one is missing and green when all are filled.

</Steps>

| Type | What to paste |
|---|---|
| `bearer` | The token, without `Bearer `. |
| `basic` | `user:password`. The placeholder says so. Luvin encodes it in Base64. |
| `apiKey` | The key. |
| `oauth2`, `openIdConnect` | An access token. It is sent as Bearer. |

A pasted value is hidden like a password. A value that starts with `{{` shows in clear, with the [colors of variables](/environments/suggestions/), because it is a name, not the secret itself.

<Aside type="tip" title="Point to a secret">
Writing `{{apiKey}}` in the credential and keeping the value in **Secrets** lets you reuse the same key in a single request and in the workflow authorization. The credential and the secret stay in sync.
</Aside>

## Where credentials are used

| Where | Does it send them? |
|---|---|
| Steps of a workflow, against the **Real API** | Yes, on every step whose operation asks for that scheme. |
| **Try it out** in a contract | Yes. It says *The environment credentials are sent (shopKey, shopBearer).* |
| The contract documentation | Yes. Swagger UI starts authorized with them: API key, bearer, basic and a pasted OAuth 2.0 token. |
| A step that already sets the header | No. A step with its own `Authorization` header, or with the API key parameter, keeps its value. |
| A workflow with its own authorization | No. Any option other than **From the contract** in the **Authorization** tab replaces them. See [Authorization of a workflow](/authorization/workflow/). |
| Cases that test a call without credentials | No, on purpose. |
| **Simulation** | No call leaves your computer. |
| Single requests | No. A request uses its own **Authorization** tab, or the collection's. |

For how each type goes out on the wire, see [Credentials of the contract](/authorization/contract-credentials/).

## How credentials are kept

- Encrypted on this computer, like secrets. They are never written to the environment file.
- They belong to one environment. A new environment does not copy them.
- They are deleted from this computer with their environment.
- They are masked as `••••` in results, reports and Dev Tools.
- After a teammate clones the workspace, they fill in their own.

## When one is missing

Before a run against the **Real API**, Luvin checks the steps of the workflow. If a step needs a credential that is empty, and neither the step nor the **Authorization** tab provides it, a notice shows above the workflow:

*Credentials are missing in “staging”: calls that need them will answer 401.*

Click **Fill in** to open the environment. The Runner shows the same notice for the workflows you tick. **Try it out** says *Credentials are missing in “staging”: the API will probably answer 401.*, with **Configure**.

You can still run. Calls that need the credential go without it, and the API usually answers `401`.
