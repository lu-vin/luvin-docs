An open environment has four sections: **Base URLs**, **Credentials**, **Variables** and **Secrets**. Variables and secrets are values with a name that you use as `{{name}}` in any field. The difference is where the value lives: a variable is written to the environment file, a secret is stored encrypted on your computer.

## Example: the PayPal sandbox environment

The PayPal example opens with the environment `Sandbox`, a variable `clientId` and a secret `clientSecret`, both empty. After you paste the two values of your sandbox app and pick a yellow label, Luvin writes this file in the `environments/` folder of the collection:

```yaml title="environments/sandbox.yaml"
# Luvin environment. Secret and credential values are not stored here: they live encrypted on each computer.
name: Sandbox
color: yellow
servers:
  paypal: https://api-m.sandbox.paypal.com
variables:
  clientId: my-sandbox-client-id
secrets:
  - clientSecret
id: 6c1f2d9e-4b7a-4e0f-9a3c-2d8b5e7f1a40
```

The workflow authorization of the example uses both values:

| You write | Luvin sends |
|---|---|
| Client ID `{{clientId}}` | `my-sandbox-client-id` |
| Client Secret `{{clientSecret}}` | The secret's value. In results, reports and Dev Tools it shows as `••••` |
| `{{paypal}}/v2/checkout/orders` in a request | `https://api-m.sandbox.paypal.com/v2/checkout/orders` |

The file lists the name `clientSecret` but never its value. The first line is a comment the app writes in English, whatever the interface language. The `id` ties the environment to its secrets on each computer. See [Environment files and teams](/environments/files-and-teams/).

## Variables

A variable is a value with a name that changes per environment: a client ID, a partner code, a test user. Under **Variables**, the tab explains: *Values that change per environment (a client ID, a partner code…). Use them as `{{clientId}}` in the inputs, in each case’s data, in the base URLs and in the credentials.*

<Steps>

1. Open the environment.
2. In **Variables**, click **+ Add variable**.
3. Type the **Name** and the **Value**.
4. Use it as `{{clientId}}` in any field. See [Use variables](/environments/use-variables/).

</Steps>

To delete one, click the trash icon at the end of its row (**Delete**). The section title shows how many variables the environment has.

### Naming rules

| The name | What you see |
|---|---|
| Has a space, starts with a digit, or uses other symbols | In red: *Use letters, digits, _ . or - (no spaces), starting with a letter or _.* |
| Is already used by another variable or secret of this environment | In red: *Another variable already has this name.* |
| Is the name of one of Luvin's generators, such as `email` or `uuid` | A warning: *Shadows the `{{email}}` generator: the variable value is used instead.* |

A name with an error is kept, so you can fix it, but `{{name}}` does not use it until it is valid. Valid examples: `clientId`, `partner_code`, `user.email`, `api-version`.

## Secrets

A secret is a variable for keys, tokens and passwords. You use it the same way, as `{{apiKey}}`. Under **Secrets**, the tab explains: *Like variables (`{{apiKey}}`), but for keys and tokens: they are saved encrypted on this computer, never in the workspace files, and show up as •••• in results and reports.*

<Steps>

1. In **Secrets**, click **+ Add secret**.
2. Type the **Name** and the **Value**. The value is hidden while you type.
3. Click the eye to see it (**Show the value**). Click again to hide it (**Hide the value**).

</Steps>

Secrets follow the same naming rules as variables, and share the list of names with them: a variable and a secret cannot have the same name. There is no switch to turn a variable into a secret. Delete the variable and add a secret with the same name.

## Where each value is stored

| Value | Where it lives |
|---|---|
| Variable | In the environment file, `environments/<name>.yaml`, as you typed it. It goes to git with the workspace. |
| Name of a secret | In the environment file, under `secrets`. |
| Value of a secret | Encrypted on this computer, with the keychain of the operating system. |
| Desktop app without a keychain available | Secret values are not stored. You type them again after you reopen the collection. |
| No workspace open (an example or loose files) | Secret values are not saved. Luvin remembers only the names. |

Credentials are stored like secrets. Values saved by requests (**Saved now**) are never written anywhere: they stay in memory while the collection is open, and Luvin clears them when you switch environments.

## Where secret values are masked

Luvin replaces each secret value, and each credential, with `••••` wherever it would show:

- In the results of workflows and in exported reports, including the inputs a case used.
- In **Sent request** of a single request, and in **Dev Tools**.
- In history: requests and runs are saved with secrets masked.
- In a copied cURL command, where the value is written as `<secret>`.

A secret is found also when it travels encoded in a URL, for example with `/` or `+` turned into `%2F` or `%2B`.

<Aside type="caution" title="What masking cannot cover">
Values shorter than four characters are not masked, because hiding them would hide single letters everywhere. Do not use secrets that short. A password you type directly in a body or an input is not a secret and is not masked: put it in a secret and write `{{password}}`.
</Aside>

## A variable or a secret?

| The value is… | Use |
|---|---|
| The same for the whole team, and harmless if someone reads it: a client ID, a region, a test customer | A variable. It travels with the workspace. |
| Personal or dangerous if it leaks: a password, a client secret, an API key, a token | A secret. Each person types their own. |
| A token that a login request returns | Neither. Save it from the response. See [Save values from a response](/requests/save-variables/). |

## Base URLs and credentials

The other two sections of the environment have their own pages:

- **Base URLs**: one per contract, plus your own for single requests. See [Base URLs](/environments/base-urls/).
- **Credentials**: the values the security schemes of the contracts ask for. See [Credentials](/environments/credentials/).
