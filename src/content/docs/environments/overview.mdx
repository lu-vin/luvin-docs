An environment holds what changes between the places where your API runs, such as local and production: the base URLs, the credentials, the variables and the secrets. You need one as soon as you run a workflow or send a request against a real API.

## Example: the same request in two environments

The shop collection has two environments. The same request, `{{baseUrl}}/customers`, goes to a different place in each:

<Tabs>
<TabItem label="local">

```yaml title="environments/local.yaml"
name: local
color: green
servers:
  baseUrl: http://localhost:8080
```

`{{baseUrl}}/customers` becomes `http://localhost:8080/customers`.

</TabItem>
<TabItem label="production">

```yaml title="environments/production.yaml"
name: production
color: red
servers:
  baseUrl: https://api.shop.test
```

`{{baseUrl}}/customers` becomes `https://api.shop.test/customers`.

</TabItem>
</Tabs>

You do not change the request. You change the active environment at the top right of the window, and the next send goes to the other server.

## What an environment holds

| Part | What it is | More |
|---|---|---|
| **Base URLs** | The address of each API in this environment, for example `https://pokeapi.co/api/v2`. One per contract, plus your own. | [Base URLs](/environments/base-urls/) |
| **Credentials** | The values the contracts ask for: a token, a user and password, an API key. | [Credentials](/environments/credentials/) |
| **Variables** | Values you reuse as `{{name}}`, such as a client ID. | [Variables and secrets](/environments/variables-and-secrets/) |
| **Secrets** | Variables for keys and tokens. Their values never go into the workspace files. | [Variables and secrets](/environments/variables-and-secrets/) |
| **Label color** | A color to tell environments apart at a glance. | [Create, rename, color and delete](/environments/manage/) |

![The Environments panel of the sidebar and an environment open, with its base URLs, credentials, variables and secrets](/media/en/environment.webp)

## One active environment per collection

Environments belong to the open [collection](/reference/glossary/). Each collection has its own list, and one of them is always the active one. A collection never has zero environments:

| Situation | The environment you get |
|---|---|
| You create a collection in a workspace | One environment called `local`, with the base URLs of the contracts you add. |
| You open the Pokédex example | `local`, pointing at `https://pokeapi.co/api/v2`. |
| You open the PayPal example | `Sandbox`, pointing at `https://api-m.sandbox.paypal.com`, with the variable `clientId` and the secret `clientSecret` still empty. |
| A collection folder has no environment files | One called **My environment**. |
| You delete the only environment | A new, empty **My environment**, with the base URLs of the contracts. |

Luvin remembers the active environment of each collection on this computer. It is not written to the files, so each teammate can have a different one active.

### Global environments

A workspace can also have global environments, which every collection of the workspace uses, as in Bruno. Put there what several collections share, such as the address of a login server. At most one global environment is active at a time, and it is optional. When you choose a collection environment, the global environment with the same name is chosen too, if there is one. See [Global environments](/environments/variable-levels/#global-environments).

## Where environments are

| Place | What you find |
|---|---|
| Top bar | The active environments, at the top right of the window, in one pill with two halves. On the left, the collection environment, with a database icon, in its color or in Luvin green without one. On the right, the global environment, with a globe, or a gray **No global** when there is none. It is always visible while a collection is open. |
| Sidebar | The **Environments** panel: click the **Environments** icon at the top of the sidebar. **Global environments** come first, then the environments of the open collection, under a title with its name. The active one has its dot filled in. A row with variables shows how many, such as **3 vars**. |
| The environment tab | Titled **Environment “name”**. It shows the active environment: its base URLs, credentials, variables and secrets, with a row of every environment at the top. |
| Runner | The **Environment** list, at the top left while you set up a run. |
| Search | Press ⌘K (Ctrl+K) and type a name. The group **Environments** lists them, and the one in use says **active**. |
| Try it out | The pill next to **Send** names the environment the call uses. Click it to configure that environment. |

## Choose the active environment

The active environment is the one Luvin uses for every run, every request and **Try it out** in a contract. Choose it in any of these places. They all change the same thing.

<Tabs>
<TabItem label="Top right">

<Steps>

1. Click the left half of the pill at the top right of the window, the one with the database icon.
2. Choose an environment. The active one has a check mark.

</Steps>

Its last option, **Configure environment…**, opens the active environment in its tab. Use the pill to switch without leaving what you are doing.

The right half opens the list of global environments, with **None** to use none, and **See all variables…**, which opens the Variables panel. With no global environment yet, it offers **Create global environment “local”**, named like the active collection environment.

![The two-half environment pill, with the menu of the global environment open: local, None and See all variables](/media/en/env-pill-split.webp)

</TabItem>
<TabItem label="Sidebar">

<Steps>

1. At the top of the sidebar, click the **Environments** icon.
2. Click an environment. Its tooltip says **Use and open this environment**.
3. It becomes active and opens in a tab titled **Environment “name”**.

</Steps>

Next to the active one, **Configure** opens it again.

</TabItem>
<TabItem label="Search">

<Steps>

1. Press ⌘K (Ctrl+K).
2. Type part of the name.
3. Choose it under **Environments**. It becomes active and opens.

</Steps>

</TabItem>
<TabItem label="Runner">

While you set up a run, open the **Environment** list at the top left and choose one. See [Open the Runner and choose the environment](/runner/open-and-environment/).

</TabItem>
</Tabs>

The environment tab always shows the active environment. Clicking another name in the row at the top of the tab makes that one active too.

## What changes when you switch

| Where | What uses the new environment |
|---|---|
| Single requests | Every `{{name}}` in the URL, params, headers, body and authorization: base URLs, variables and secrets. |
| Workflows | The base URL of each contract, the credentials, and every `{{name}}` in inputs, cases and steps. |
| Try it out and the contract documentation | The server and the credentials of the contract. |
| Runner | The same active environment. Its name shows in the results. |
| Run confirmation | When a workflow has steps that create, change or delete data, Luvin shows *These steps modify data in the “name” environment:* before a real run. After you switch, it asks again. |

![Before running PayPal's Create order: the notice that a POST modifies data in the Sandbox environment](/media/en/test-run-confirm.webp)

Luvin also clears what the previous environment obtained, so it never reaches the new one:

- Values saved by requests (**Saved now**).
- OAuth 2.0 tokens.
- Cookies of single requests.

A token obtained with `local` is no longer sent to `production`. Send the login again in the new environment; an OAuth 2.0 token is fetched again on the next send. This happens every time the active environment changes: from the pill, from the **Environments** panel, when you create an environment or delete the active one, and when a mock environment becomes active.

Some things stay as they were:

| What | Why |
|---|---|
| The results of the last run | They keep the environment they ran with. A report exported later still names that one. |
| History | Each entry keeps the name of the environment it used. |

<Aside type="caution" title="Check the pill before a real run">
The pill at the top right is the only place outside the sidebar that names the active environment. A red label for production makes it hard to miss.
</Aside>
