A request you saved has no contract that says which fields the API requires. You know it, so you tell Luvin. Do this when you build a workflow from saved requests. The answer decides which data the workflow asks for and which negative cases Luvin generates.

Luvin does not stop you to ask when you add a request. It marks the steps that are missing the answer, and you mark the fields when you want.

## Example: Create order

You add the request **Create order** to a workflow. Its card shows **required not marked**. You click **Mark required fields** in its panel, tick what the API requires and click **Save**.

<Tabs>
  <TabItem label="In the dialog">

| Group | Row | State |
|---|---|---|
| **Query params** | `bank` | **required** |
| **Headers** | `x-api-key` | **required** |
| **Body** | `address/city` | **required** |

  </TabItem>
  <TabItem label="In the request file">

```yaml title="requests/create-order.request.yaml" {1-4}
requiredFields:
  - query:bank
  - header:x-api-key
  - body:address/city
```

  </TabItem>
</Tabs>

## Why it matters

An operation from a contract carries this information: the contract says that `bank` is required. A saved request is only a call that worked once, so it does not say whether `bank` is required or just present.

What you mark has two effects:

- **Required data.** When you turn a fixed value into an input, that input is required only if you marked its field as required. See [Build from saved requests](/design/from-requests/).
- **Negative cases.** For each required input, Luvin generates a case that leaves it out, **Without the required input "…"**, and checks that the API rejects it. See [Cases](/test/cases/).

Anything you leave unmarked is optional. Until you answer, the step has no negative cases.

<Aside type="note">
This applies to steps that come from **Collection requests**. A step from a contract operation is never marked, because the contract already says what is required. A request generated from a contract also comes with its required fields marked. See [Generate requests from a contract](/requests/generate-from-contract/).
</Aside>

## See which steps are missing the answer

A step built from a request that nobody has answered for shows **required not marked** on its card. Point at it to read why: **Which fields the API requires isn’t marked yet: without them there are no negative cases for this step.**

When there is at least one, a bar at the top of the canvas sums them up: **2 step(s) without required fields marked: without them there are no negative cases for those steps.** The bar goes away when every step has an answer.

A request with nothing to mark, for example one whose only fields are in the path, is never flagged.

![The bar 1 step(s) without required fields marked, with Mark, above a step built from the request Create order](/media/en/design-required-bar.webp)

## Mark the required fields

### All the pending steps at once

<Steps>
1. In the bar at the top of the canvas, click **Mark**.
2. The dialog lists every pending request, one after the other, under its name. Its title says how many: **Which fields does the API require in these 2 requests?** With one request, it names it: **What does the API require in «Create order»?**
</Steps>

### One step

<Steps>
1. Click the step that comes from a request. Its panel starts with **From the request “Create order”**.
2. On the right of that line, click **Mark required fields**. Under it, the panel says why: **Without them there are no negative cases for this step (for example, “without bank it must be rejected”).**
</Steps>

After you have answered once, the link reads **Required fields (3)**, with the number you marked. Click it to change your answer. Pointing at it shows *Which fields of this request the API requires*.

![The top of the panel of a step built from a request: From the request “Create order” and the link Required fields (1)](/media/en/design-request-step.webp)

## The dialog

Under the intro, the dialog lists every field of the request in four groups:

| Group | What it lists |
|---|---|
| **Path** | The parameters of the path, such as `{id}`. They are always required and you cannot untick them: without them the URL points to another resource. |
| **Query params** | The query parameters of the request. |
| **Headers** | The headers of the request, except the ones Luvin adds from other tabs: `Content-Type`, `Authorization`, `Content-Length` and `Host`. |
| **Body** | The simple fields of the body (text, number, true/false), written as their path, for example `bank` or `address/city`. |

Each row has a box, the name of the field, the value the request sends now and the word **required** or **optional**.

<Steps>
1. Tick the fields the API requires.
2. To change them all at once, click **Mark all** or **None**. With several requests, each one has its own **Mark all** and **None**.
3. Click **Save**.
</Steps>

**Cancel**, the **×** or Esc close the dialog without saving. The steps stay marked until you answer.

Saving with no box ticked is an answer too: it says that nothing is required beyond the path parameters.

![The dialog What does the API require in «Create order»?: Mark all and None, the Body group with customer required and currency optional, and Cancel and Save](/media/en/design-required-fields.webp)

## Where it is saved

At the bottom of the dialog: **Saved in the request: it applies to every workflow that uses it.** The answer is saved in the request file, not in the workflow, so you answer once for each request. In a workspace the list is in `requests/<name>.request.yaml`, under `requiredFields`, as in the example at the top. Each item has the place of the field (`query`, `header` or `body`) and its name. Header names are written in lower case. Path parameters are not listed, because they are always required.

The workflow does not change when you save. Luvin rebuilds the contract it keeps for your requests, and the steps read the new answer from there. See [Build from saved requests](/design/from-requests/).
