Contracts often leave out statuses that any API can answer: 429 when you send too many requests, 503 during maintenance, 500 when the server fails. The route editor takes any status, declared or not.

## Example: retry a 429 of getPokemon

The PokéAPI contract does not declare 429 for `getPokemon`.

<Steps>
1. Open **Pokemon card** and click the **Design** tab.
2. On the card of `getPokemon`, click **＋ What to do if it fails**.
3. In **If it responds**, type `429`. The statuses next to **the contract says:** do not include it, and that is fine.
4. Click **Retry**, leave **Wait** `2` **s, up to** `3` **times**, and click **Add**.
</Steps>

<Tabs>
<TabItem label="On the canvas">

The card gets the row `429 ↻ retries up to 3 · every 2 s`, with a blue loop back into the card.

</TabItem>
<TabItem label="In the YAML">

```yaml title="pokemon.arazzo.yaml"
onFailure:
  - name: pokemonNotFound
    type: end
    criteria:
      - condition: $statusCode == 404
  - name: retry429
    type: retry
    retryAfter: 2
    retryLimit: 3
    criteria:
      - condition: $statusCode == 429
```

</TabItem>
</Tabs>

## Which statuses you can type

**If it responds** takes only digits, up to three. Anything else is dropped as you type. **Add** stays off until the status has three digits and you chose what to do.

A route on failure only runs when the step fails. A status the step already counts as success, such as its 200, never reaches it.

## A status for every step

When the same status can come from any call, as a 429 from a rate limit or a 503 from maintenance, add it once as a rule of the workflow instead of one route per step. Open **Start**, click **＋ Rule for every step** and fill in the editor the same way. See [Rules for every step](/design/routes-panel/#rules-for-every-step).

## Common statuses

| Status | Usual meaning | A sensible route |
|---|---|---|
| 401 | The token expired | **Renew and retry**, with the login workflow. |
| 409 | Conflict with the current state | **Go to another step**, for example one that reads the current state. |
| 429 | Too many requests | **Retry**. Raise **Wait** if the API asks to wait longer. |
| 500 | The server failed | **End the workflow**, or no route, so the run fails and you see it. |
| 503 | Service unavailable | **Retry**, or **End the workflow**. |

Luvin waits only what the route says. It does not read a `Retry-After` header of the response.

## Declared statuses without a route: one click

A status the contract declares and nothing handles is a red row on the card, `422 ✕ no route: the workflow fails`. In the **Success and routes** tab of the step panel, the same status has three buttons:

| Button | What it adds |
|---|---|
| **Ends** | A route that ends the workflow on that status. The notice says **Route added: if it responds 422, the workflow ends.** |
| **Retries** | A route that retries the step every 2 seconds, up to 3 times. The notice says **Route added: if it responds 422, it retries every 2 s, up to 3 times.** |
| **Choose what to do** | The route editor, with the status filled in. |

Each notice has **Undo**.

## What you see afterwards

| Where | What appears |
|---|---|
| The card | The row of the new route, with its arrow, and a pencil to change it. |
| The **Success and routes** tab | The route in the **Routes** list, in words and with its Arazzo line. |
| [To review](/design/review/) | If the status was declared, one fewer **without a route**. |
| **Cases** | A generated case, **getPokemon responds 429 → retry429**, that simulates that response. |
| Results of a real run that got a 429 | The step notes **Status 429 is not documented in the contract of …**. |

That last message is a hint, not a mistake in your workflow. If the API really answers that status, add it to the contract: it then shows next to **the contract says:**, and as a red row while nothing handles it. See [Edit a contract](/contracts/edit/).
