You do not need an OpenAPI contract to build a workflow. If you have saved requests, for example imported from Postman or Bruno, add them to the canvas and each one becomes a step. Use this when the API has no contract, or you only have a collection of requests.

A *request* is one saved API call: a method, a URL, headers and a body. See [Requests](/requests/overview/) and [Import from Postman or Bruno](/get-started/import/).

## Example: Create order and Get order

You saved two requests, **Create order** and **Get order**. The script of **Create order** saves the new id, as many Postman collections do:

```js
pm.collectionVariables.set("order_id", pm.response.json().id);
```

You add both requests to the canvas.

| You add | Luvin creates | What it keeps |
|---|---|---|
| Request **Create order** | A step titled **Create order**, with the id `createOrder` | The same URL, headers and body, with the `{{variables}}` of the environment |
| Request **Get order** | A step titled **Get order**, with the id `getOrder` | The path, where `{{order_id}}` now comes from `createOrder` |

Luvin read the script without running it: `{{order_id}}` in **Get order** is the `id` that **Create order** returns. The step `getOrder` takes it from there, and `createOrder` gets a new output, `order_id`. You did not have to send anything first.

Without that script, Luvin learns the responses on the first run and then suggests the connection. See [Accept the suggested connections](#accept-the-suggested-connections).

## Add a request as a step

Open the workflow and go to the **Design** tab. There are three ways:

- **On an empty canvas**, click **Build from the collection's requests**. **Add a step** opens. Click the requests in the order you want: each one goes at the end of the workflow. Close it when you are done.
- **At any time**, click **＋ Step** in the toolbar, or press `/`. In **Add a step**, open **Collection requests** (the requests of the collection, grouped by folder) and click a request, or **+** on its row. Type in **Search operation…** to filter. The step goes after the selected step or, if none, at the end.
- **From the sidebar**, drag a request from the collection tree onto the canvas.

Only HTTP requests with a URL can be added. For anything else Luvin says **Only HTTP requests with a URL can be added to a workflow.**

![Add a step in a collection without contracts: Collection requests with Create order (POST) and Get order (GET)](/media/en/design-requests-palette.webp)

## What the step keeps

The step is sent exactly like the request: same URL, parameters, headers and body, with the `{{variables}}` of the environment kept. Luvin does not create inputs: what does not come from an earlier step keeps the value of the request.

**Its title is the name of the request.** The canvas, the sidebar, the results and the reports show **01 - Login**, as you named it in Postman.

**Its id is short and readable.** Luvin takes the name of the request without its leading numbering (`01 - `, `1.`, `#3`), drops filler words (*the*, *of*, *and*, *is*, *de*, *la*, *y*…) and keeps up to four words in camelCase:

| Request | Step id |
|---|---|
| **Create order** | `createOrder` |
| **01 - Login** | `login` |
| **02 - Instrument is inactive and canonical** | `instrumentInactiveCanonical` |

If the id is already taken, a number goes at the end: `login2`. The id appears under the title in the step panel and in the YAML, because expressions such as `$steps.login.outputs.token` use it. Ids that already exist never change, even if you rename the request.

**Its success criterion** comes from the request's script when the script expects one status. A request that checks `pm.response.to.have.status(400)`, or `expect(res.status).to.equal(400)` in Bruno, gets `$statusCode == 400`: the step passes when the API answers the error it expects. See [Expect an error](/recipes/expected-error/#from-a-postman-request-that-expects-an-error). Otherwise it is the lowest 2xx status Luvin knows for the request, or `$statusCode < 400` if it knows none.

## How Luvin wires the data

When you add a request, Luvin looks at the earlier steps and replaces the values that come from them. It does not run anything.

1. **What the scripts save.** If an earlier request's script saves a value from its response, a later `{{variable}}` with that name comes from that step. For example, **Products by category** has `pm.collectionVariables.set("productId", json.products[0].id)`, and **Product detail** uses `/products/{{productId}}`. Then `productId` in **Product detail** comes from `products/0/id` of the step `productsByCategory`, with a new output there. This works before Luvin knows any response.
2. **What the responses say.** Once Luvin knows what an earlier step answers, a value takes an output or a response field with the same name, or a composed one: `customerId` takes `customer/id`.
3. **An id in the path.** A path parameter such as `orderId` can take the `id` of the step right before it. Only if that step is about the same thing: a `userId` never takes the id of a step about products.
4. **An input with the same name**, if the workflow already has one.

Generated data is never replaced. A `{{$randomFirstName}}`, `{{$randomEmail}}` or `{{$guid}}` stays as it is, so each run sends a new value.

The login token is wired the same way: Luvin reads the login's script and passes its token to the next steps. See [Pass the login token to the next steps](/authorization/token-from-login/#luvin-connects-it-while-you-build).

## Mark the required fields

A request does not say which fields the API requires. Luvin does not ask while you build: a bar above the canvas says how many steps have none marked, for example *2 step(s) without required fields marked: without them there are no negative cases for those steps.* Click **Mark** to answer for all of them in one list, when you want.

In the panel of a step, **Mark required fields** (or **Required fields (n)** once marked) opens the same list for that request. The answer applies to every workflow that uses the request. See [Required fields](/design/required-fields/).

![The bar 1 step(s) without required fields marked, with Mark, and the card of the step with required not marked](/media/en/design-required-bar.webp)

## How Luvin builds a contract for you

An Arazzo file needs a contract to point to. Luvin creates one from your requests, one per base URL, in the folder `requests/_contracts` of the collection. Each request is an operation. The first line says it is generated: do not edit it, because Luvin rewrites it when a request changes.

A contract cannot have two operations with the same method and path. If two requests share them (for example, two variants of `GET /items`), Luvin puts the second in a sibling contract, such as `baseUrl2`. For you they are still **one API per base URL**:

- the workflow's **Authorization** tab shows one card, `baseUrl`, and what you choose applies to all its contracts;
- the environment has one base URL for it;
- on the canvas, its steps say `source baseUrl`.

Only the **YAML** tab lists each generated contract, with a note that explains why.

A request does not say what the API answers, so the contract starts with no responses.

## Luvin learns the responses

Luvin learns what each request answers from three places:

- The first time you run the workflow against the **Real API**. Simulated runs do not count.
- The examples saved in the request.
- The last response you received when you sent the request on its own.

You can also teach it without a run. Click the step. The panel starts with **From the request “Create order”**. When Luvin does not know the response yet, it says so and offers **Try this step**. For a GET this sends the request. For any other method it first warns **This sends the POST for real and may create or change data.** and offers **Send anyway** or **Cancel**. Once it knows the response, the note says so.

## Accept the suggested connections

With the responses known, Luvin can see that a value you wrote by hand comes from an earlier step. For example, the path of **Get order** has `{{order_id}}`, no script saves it, and **Create order** returns an `id`. A bar appears above the canvas: **Luvin found 1 connection(s) between steps**.

| Button | What it does |
|---|---|
| **Connect all** | Applies every suggestion. |
| **Connect** | Applies that one. |
| **Ignore** | Hides that one. |
| **Hide** / **Show** | Folds or unfolds the list. |

Each line names the step, the value and where it would come from. After a run, the other tabs show **With the last run, Luvin found 1 connection(s) between steps.** with the link **Review in Design**.

Luvin does not connect anything until you accept. **Undo** reverts it. Generated data such as `{{$randomEmail}}` is never suggested. [Connect data between steps](/design/wire-data/) explains the result.

![The bar Luvin found 1 connection(s) between steps: the orderId of the second step, written as order_id, would come from the id of the first](/media/en/design-connections-bar.webp)

## Choose data to vary

Since the steps keep the values of the requests, the workflow starts with no inputs (**▶ Start · no inputs**), and a case has nothing to change. Pick the values you want to vary.

<Steps>
1. On the **Start** card, click **Choose variable data…**.
2. In **Data to vary per case**, tick the values. Each row shows where it is, for example `query · bank`, and its current value.
3. Click **Turn into inputs**. The number of values you ticked is in the button.
</Steps>

Each value becomes an input of the workflow that keeps the current value as its default, so the happy path does not change. If the same value is used in several steps, one input feeds all of them. An input is required only when its parameter or field is required. Path parameters always are.

To change one value, point at it on a card and click **→ input**. When the workflow already has inputs, the **Start** card shows **+ Turn another fixed value into an input** instead.

The same dialog opens from the **Cases** tab, with the button **Choose data to vary**. Having inputs lets Luvin generate cases that send empty or invalid data. See [Cases](/test/cases/).
