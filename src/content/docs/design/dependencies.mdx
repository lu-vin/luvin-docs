A workflow can use another workflow, of the same file or of another Arazzo file of the collection, in two ways. It can **call** it as one step, or it can **depend on** it, which means the other workflow runs first and this one reads what it returned. Use this to avoid building the same chain twice, for example "log in" or "create a customer".

## The example: Battle matchup

In the Pokédex example, **Type explorer** takes a type such as `fire`, finds the first Pokémon of that type and returns `pokemon`, `strongAgainst` and `isLegendary`. **Battle matchup** depends on it: it uses the type that **Type explorer** is strong against to look for a rival.

In the file, this is one line, `dependsOn`, and a value that reads an output:

<Tabs>
  <TabItem label="In the app">

![A workflow with a Depends on card above Start, listing the outputs of the workflow it depends on, and two steps that use them](/media/en/builder-depends.webp)

  </TabItem>
  <TabItem label="In the YAML">

```yaml title="pokemon.arazzo.yaml" {2,9}
- workflowId: battleMatchup
  dependsOn: [typeExplorer]
  steps:
    - stepId: getRivalType
      operationId: $sourceDescriptions.pokeapi.getType
      parameters:
        - name: idOrName
          in: path
          value: $workflows.typeExplorer.outputs.strongAgainst
```

  </TabItem>
</Tabs>

A runnable version: [One workflow logs in, others reuse its token](/recipes/depends-on/).

## Make a workflow depend on another one

<Steps>
1. Open the workflow that needs the data, and go to the **Design** tab.
2. Click **Start**, the green button at the top of the canvas. Its panel opens over the canvas, on the right.
3. Under **Depends on**, open **Add a workflow…** and choose a workflow.
</Steps>

A card **⇡ Depends on** appears above **Start**. It lists each workflow and its outputs. If a workflow has no outputs, the card says **no declared outputs**: open that workflow and add outputs on its **End of workflow** card. See [Outputs](/design/outputs/).

The panel says **This Arazzo has no other workflows.** when the file has only one workflow. Add another first. See [Create a workflow](/design/create/).

To stop depending on a workflow, click the bin next to its name in the same panel.

![The Start panel with its inputs and the list Add a workflow… open, with the groups In this file and In auth.arazzo.yaml](/media/en/design-depends-options.webp)

## Use its outputs

The outputs of the workflows you depend on are available to every step, as `$workflows.<workflow>.outputs.<name>`. There are two ways to connect one:

- In the step panel, in the **Data** tab, open the list of a parameter. Each dependency has a group, **Workflow “Type explorer” (depends on)**, with its outputs.
- Drag from the dot of an output in the **Depends on** card to a parameter of a step. [Connect data between steps](/design/wire-data/) explains both ways.

On the card, the parameter shows where the value comes from, for example **← strongAgainst · Type explorer**.

## Call a workflow as a step

<Steps>
1. Click the step after which the call should go. With no step selected, it goes at the end.
2. Click **＋ Step** in the toolbar at the top of the canvas, or press `/`.
3. In the menu, go to **Workflows in this Arazzo**. It lists the other workflows of the file, each marked **WORKFLOW**. Type part of its name to filter.
4. Click the workflow.
</Steps>

The step is named after the workflow. Luvin does the wiring for you:

- Each required input of the called workflow becomes a parameter of the step, taken from an earlier step or from an input of this workflow, as for any other step. The panel lists them under **Workflow inputs**.
- Every output of the called workflow becomes an output of the step, so the next steps can read it.

The card shows **WORKFLOW** and **⤷ calls workflow typeExplorer**, and so does the step panel, under the title. For a workflow of another Arazzo file it adds that file, for example **calls workflow login · auth.arazzo.yaml**, and lists the inputs that workflow asks for, the same as for one of this file. If the workflow does not exist, it adds **missing**.

![The panel of a step that calls browseProducts: calls workflow browseProducts, the input limit under Workflow inputs and the outputs sku and price](/media/en/design-call-workflow.webp)

### See the steps of the called workflow

When the called workflow is in the same file, its card has a link, **▸ See its 2 steps**, with the number of steps it has. Click it to list them on the card, each with its number, method and title, without leaving the canvas. **▾ Hide its steps** folds them again.

Workflows of other Arazzo files are not listed this way. Open that file to see them.

![A step that calls browseProducts with its steps unfolded: 1 GET List products and 2 GET Product detail](/media/en/design-sub-steps.webp)

## Use a workflow of another Arazzo file

The workflow you need can be in a different Arazzo file of the same collection, for example a `login` that every file reuses. Luvin runs it as if it were in this file.

<Tabs>
  <TabItem label="In the app">

<Steps>
1. Open the **Design** tab of the workflow, and click **Start**.
2. Under **Depends on**, open **Add a workflow…**. The list has a group **In this file** and one group per other Arazzo file, **In auth.arazzo.yaml** for example.
3. Choose the workflow of the other file.
</Steps>

Luvin adds the other file to `sourceDescriptions` as a source of `type: arazzo`, once, and writes the reference. The **Depends on** card shows the name of the workflow and its file.

![The Depends on card above Start: the workflow login of auth.arazzo.yaml and its output token](/media/en/design-depends-card.webp)

To call it as a step instead, click **＋ Step**. The group **From other Arazzo files** of the menu lists those workflows, each marked **WORKFLOW** with its file. Click one. Luvin adds the source the same way.

  </TabItem>
  <TabItem label="In the YAML">

```yaml title="profile.arazzo.yaml" {3,7,16}
sourceDescriptions:
  - { name: dummyjson, url: ./dummyjson.openapi.yaml, type: openapi }
  - { name: auth, url: ./auth.arazzo.yaml, type: arazzo }
workflows:
  - workflowId: myProfile
    summary: Read my profile after logging in (another document)
    dependsOn: [$sourceDescriptions.auth.login]
    steps:
      - stepId: getMe
        operationId: getMe
        parameters:
          - { name: Authorization, in: header, value: 'Bearer {$workflows.login.outputs.token}' }
  - workflowId: loginAsStep
    steps:
      - stepId: auth
        workflowId: $sourceDescriptions.auth.login
        outputs: { token: $outputs.token }
```

  </TabItem>
</Tabs>

The workflows of an `arazzo` source are named `$sourceDescriptions.<source>.<workflowId>`. You can use that name in:

| Where | What Luvin does |
|---|---|
| `dependsOn` of a workflow | Runs it first, once, with the workflows it depends on in its own file. Read its outputs as `$workflows.<workflowId>.outputs.<name>`, with the workflow id only. |
| `workflowId` of a step | Calls it at that point. Read its outputs as `$outputs.<name>` in the step's `outputs`. |
| `workflowId` of a `goto` or `retry` action | Runs it when the route is taken. See [Add or change a route](/design/branch-menu/). |

A workflow called as a step uses its own default or example value for every input the step does not pass.

:::note
The other file is found by its file name, so it must be in the same collection. A source of type `arazzo` does not appear in the contracts list. The analysis shows an info note: **Source "auth" is another Arazzo document (auth.arazzo.yaml): its workflows can be used as `$sourceDescriptions.auth.<workflowId>`.**
:::

Runnable example: [Use a workflow from another Arazzo file](/recipes/cross-document/).

## Which one to use

| | Call as a step | Depends on |
|---|---|---|
| When it runs | At that point of the steps, in every case. | Once, before the cases of the run. |
| Inputs | You connect them as parameters of the step. | The values of that workflow's own **Inputs** tab. |
| Where you read the outputs | The outputs of the step. | `$workflows.<workflow>.outputs.<name>` |
| If it fails | The step fails, and the reason names the step where the other workflow stopped. | The cases do not run. Each ends as inconclusive, with the reason: **The workflow could not be prepared: the workflow “…” it depends on failed.** |

## What runs first

When you press **Run**, Luvin runs the workflows you depend on, in the order they need, before the cases. A workflow that depends on others runs after them. In **Simulation** they are simulated too, and against the **Real API** they call the API. The results open with a **Preparation** block that shows them. See [Results](/test/results/).

Set the inputs of a dependency in its own **Inputs** tab. **Type explorer** has the input `type` with the default `fire`, and **Battle matchup** has no inputs of its own.

## Limits

- **Other files must be in the collection.** If the file of an `arazzo` source is not loaded, or the workflow does not exist in it, the analysis says so and the cases end as inconclusive.
- **No circles**, also across files. If A depends on B and B on A, Luvin does not run them and says so with a message like **The workflows depend on each other in a circle**.
- **Five levels.** Workflows called as steps can be nested up to five levels. Beyond that the step fails with **Too many levels of nested sub-workflows.**
- **A missing workflow is an error.** If a workflow depends on one that does not exist, the card shows **missing** and the cases end as inconclusive with the reason.

<Aside type="note">
Deleting a workflow that others use is possible, but they show errors until you adjust them. See [Organize a workflow](/design/organize/).
</Aside>
