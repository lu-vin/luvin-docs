This page answers "how do I…?" for the situations people meet most when they design a workflow. Each one has the situation in one line, how to do it in the **Design** tab, what Luvin writes in the Arazzo file, and the page that explains it in full.

The examples use the Pokédex example of the app and a generic shop: log in, list products, create an order and read it back.

<Aside type="tip" title="Canvas or YAML">
Most situations are done on the canvas. A few, such as criteria on the body or failure routes on a field of the response, are written in the [YAML tab](/design/arazzo-editor/). Each situation says which one. Whatever you write by hand is kept when you go back to the canvas, and **\{ \} YAML** shows the file next to the canvas while you work.
</Aside>

## Pass data from one step to the next

### The token of the login goes to the next steps

The login returns `accessToken`, and the next calls need it as their authorization.

When Luvin recognizes the token in the response of the login, or in the script of a Postman or Bruno request, it connects it as you add the steps. A notice says how many steps use it, with **Undo**. Otherwise, click the login step and, in **Outputs**, choose the field to use as authorization in the following steps.

The login card shows **🔑 signs in**, and each step that uses the token shows **🔑**. The header is in the **Authorization** tab of each step, not under **Headers**.

```yaml
- stepId: login
  outputs:
    token: $response.body#/accessToken
- stepId: createOrder
  parameters:
    - name: Authorization
      in: header
      value: Bearer {$steps.login.outputs.token}
```

The **Sign in and use the token** pattern of **＋ Step** does the same in one move. Details: [Pass the login token to the next steps](/authorization/token-from-login/).

### An id from a response goes in the path of the next step

You add `GET /pokemon-species/{idOrName}` after `GET /pokemon/{idOrName}`, and the second needs the `id` of the first.

<Steps>
1. Add the two operations with **＋ Step**.
2. Look at the second card. Its `idOrName` shows the chip **← id · from 1**, with a `?` in front: Luvin connected it for you and added the output `id` to the first step.
3. If the source is not the one you want, click the step and, in its **Data** tab, choose another one in the **Source** list.
</Steps>

Click the second card to see the data line from the output `id` of step 1 to `idOrName`.

![A new workflow with two steps: Start has the input idOrName, the first step reads it and gives id, and the second shows the chip ← id · from 1](/media/en/design-auto-wired.webp)

<video controls muted playsinline preload="metadata" poster="/media/en/design-wire.webp" src="/media/en/design-wire.mp4"></video>

```yaml
- stepId: getPokemonSpecies
  parameters:
    - name: idOrName
      in: path
      value: $steps.getPokemon.outputs.id
```

The `?` means Luvin is less sure: review it. Details: [Connect data between steps](/design/wire-data/).

### A value nobody provides becomes an input

When no earlier step returns a value the step needs, Luvin creates an input of the workflow with the name of the value. In the image above, **Start** has `idOrName`, created when you added the first step.

To do it yourself, open the **Source** list of the value and choose **New input “name”**. The input is created as required.

```yaml
inputs:
  type: object
  required: [idOrName]
  properties:
    idOrName: { type: string }
steps:
  - stepId: getPokemon
    parameters:
      - { name: idOrName, in: path, value: $inputs.idOrName }
```

You fill the inputs in the **Inputs** tab. See [Inputs](/test/inputs/).

### A fixed value becomes an input, and back

A step sends `currency: EUR` always. You want cases that try other currencies.

<Steps>
1. On the card, point at the fixed value. **→ input** appears next to it.
2. Click **→ input**. **Start** gets the input `currency`, with `EUR` as its value, and the step reads it.
3. To pick several at once, click **+ Turn another fixed value into an input** on **Start** (or **Choose variable data…** when there are no inputs yet), tick the values in **Data to vary per case** and click **Turn into inputs**.
</Steps>

![The createOrder card with the → input button next to the fixed value of currency](/media/en/design-promote-one.webp)

![The Data to vary per case dialog with two values ticked: currency and address/city](/media/en/design-pick-data.webp)

To go back, there is no single button. Do it in two moves:

<Steps>
1. Click the step and, in the **Source** list of the value, choose **Fixed value…**. Type the value.
2. Click **Start** and delete the input with its bin.
</Steps>

If you delete an input that a step still uses, the bar **This workflow is missing data** appears. Right after turning values into inputs, **↶ Undo** also brings back the fixed values.

<video controls muted playsinline preload="metadata" poster="/media/en/design-promote.webp" src="/media/en/design-promote.mp4"></video>

```yaml
inputs:
  properties:
    currency:
      type: string
      description: createOrder · body · currency
      example: EUR
steps:
  - stepId: createOrder
    requestBody:
      payload:
        currency: $inputs.currency
```

Details: [Parameters and body](/design/parameters-and-body/#turn-a-fixed-value-into-an-input).

### A field that comes from a list

`listProducts` returns `items`, a list, and the next step needs the `sku` of one product.

<Steps>
1. Click the next step and open the **Source** list of the value.
2. Under `listProducts`, choose **items/sku (from a list: you choose which at run time)**.
</Steps>

The field is shown without its position: `items/sku`. In the file Luvin writes the first position, and when you run a case it pauses after the step and asks which item to continue with. The outputs of the step also let you expose the **whole list**.

![The outputs of listProducts: the note about the list, the whole list tag and items/sku ticked](/media/en/design-list-outputs.webp)

```yaml
- stepId: listProducts
  outputs:
    sku: $response.body#/items/0/sku
```

Details: [Outputs](/design/outputs/#fields-that-are-lists) and [Choose an item from a list](/test/lists/).

### Nested objects and lists in a body

The order has an `address` object and a list of `lines`.

<Steps>
1. Click the step. In the **Data** tab, under **Body**, fields inside objects appear with their path: `address/city`, `address/zip`. Give each one a source.
2. For the list, click **Edit as JSON**, write the items and click **Apply**. Use `"$inputs.name"` or `"$steps.step.outputs.value"` as values.
</Steps>

![The Edit as JSON box of createOrder with the address object and the lines list](/media/en/design-body-json.webp)

```yaml
requestBody:
  contentType: application/json
  payload:
    customer: Ana
    address: { city: Madrid, zip: '28001' }
    lines:
      - { sku: $steps.listProducts.outputs.sku, qty: 1 }
```

Details: [Parameters and body](/design/parameters-and-body/#edit-the-body-as-json).

### The same operation twice in one workflow

You want to read a Pokémon, and later another one. Add the same operation again with **＋ Step**, or select the step and press **⌘D** to duplicate it. The new step gets another id: `getPokemon2` when you add it, `getPokemon_2` when you duplicate it. Each step has its own parameters and outputs, so later steps can read either one.

```yaml
- stepId: getPokemon
  operationId: $sourceDescriptions.pokeapi.getPokemon
- stepId: getPokemon2
  operationId: $sourceDescriptions.pokeapi.getPokemon
```

To give it a clearer title or id, click the step and change them at the top of its panel. Details: [Organize a workflow](/design/organize/).

## Change the order or undo

### Reorder, remove, undo and redo

<Steps>
1. Drag a card above or below another card, or select it and press **⌥↑** or **⌥↓**.
2. If the step now runs before the one that gives it data, the bar **Check the order:** says so. Click **Undo** in the bar.
3. To remove a step, click **×** on its card, or select it and press **⌫**. A window lists what breaks; click **Remove the step**.
4. **↶ Undo** and **↷ Redo** above the canvas (⌘ + Z and ⇧ + ⌘ + Z) step through your changes.
</Steps>

![The Check the order bar: getOrder uses data from createOrder, which now runs after it](/media/en/design-order-warning.webp)

<video controls muted playsinline preload="metadata" poster="/media/en/design-organize.webp" src="/media/en/design-organize.mp4"></video>

Details: [Organize a workflow](/design/organize/).

### Copy steps to another workflow, or make them a workflow of their own

<Steps>
1. Shift + click the steps. A bar says **3 steps selected**.
2. To copy them, press **⌘C**, open the other workflow, select a step and press **⌘V**. Ids that exist get `_2`.
3. To reuse them, click **⇪ Extract to a workflow** (only consecutive steps), give it a name, read the preview and click **Extract**.
</Steps>

Details: [Copy, duplicate and extract steps](/design/copy-and-extract/).

## Decide what counts as success

### Success by status

Click the step, open the **Success and routes** tab and, under **It succeeds if**, choose the status you expect after `$statusCode ==`. Luvin writes `$statusCode == 201`.

### Success by a condition on the response

The canvas edits the status. Conditions on the body or the headers are written in the YAML tab, inside `successCriteria`. All the criteria must hold. The card and the panel list them with their type, and the panel offers **Edit in the YAML**.

| Kind | Example |
|---|---|
| Simple | `- condition: $response.body#/capture_rate >= 0` |
| Regex | `- context: $response.header.Content-Type`<br />`  condition: ^application/json`<br />`  type: regex` |
| JSONPath | `- context: $response.body`<br />`  condition: $.abilities[?(@.is_hidden == false)]`<br />`  type: jsonpath` |
| XPath (XML responses) | `- context: $response.body`<br />`  condition: /order/status`<br />`  type: xpath` |

A JSONPath written as a comparison, such as `$.legendary == true`, is never met. **⚠ to review** flags it and offers **Change it**, which rewrites it as `$response.body#/legendary == true`. See [To review](/design/review/).

![The Success and routes tab of getSpecies: the status after $statusCode == and an extra criterion with its type and Edit in the YAML](/media/en/design-criteria-panel.webp)

Details: [Success and errors](/design/success-and-errors/), [Success criteria](/reference/criteria/) and the recipe [Check more than the status](/recipes/criteria/).

## Decide what happens after a step

Each step can have routes: what to do if it fails, and where to go if it passes and a condition holds. They are rows on the card, in red (**On failure**) and green (**If it passes and matches**), with an arrow on the left to where they go.

<video controls muted playsinline preload="metadata" poster="/media/en/design-errors.webp" src="/media/en/design-errors.mp4"></video>

### An expected error ends the workflow

"The Pokémon does not exist" is a known outcome, not a crash.

<Steps>
1. On the card, find the red row **404 · no route**, and click **Choose what to do**. Or click **＋ What to do if it fails** and type `404`.
2. Click **End the workflow**, check the preview and click **Add**.
</Steps>

The arrow of the route goes to **End of workflow**.

```yaml
onFailure:
  - name: on404
    type: end
    criteria:
      - condition: $statusCode == 404
```

Luvin also generates a case that simulates the 404 and checks that the route runs. Runnable example: [Expect an error](/recipes/expected-error/).

### Retry with a wait and a limit

In the route editor, choose **Retry**. It starts at a wait of 2 seconds and up to 3 times; change both numbers before you click **Add**. In the panel, a status without a route also has **Retries**, which writes the same in one click. Luvin never waits more than 10 seconds between two tries against the real API.

```yaml
onFailure:
  - name: retry429
    type: retry
    retryAfter: 2
    retryLimit: 3
    criteria:
      - condition: $statusCode == 429
```

To sign in again before the retry, choose **Renew and retry** and the login workflow. See [Add or change a route](/design/branch-menu/).

### Go to another step

Choose **Go to another step** and the step in **Go to step**. On the card, a red dashed arrow goes from the row to that step. A route that goes back shows the runner's limit: **(the runner stops at 200 executions)**.

![The canvas: the 409 row of createOrder goes to listProducts, with a red dashed arrow on the left of the cards](/media/en/design-jump-line.webp)

```yaml
onFailure:
  - name: on409
    type: goto
    stepId: listProducts
    criteria:
      - condition: $statusCode == 409
```

To send an error to a step that does not exist yet, choose **or a new step…**. See [A new step for a route](/design/branch-new-step/).

### Continue in another workflow

Choose **Continue in another workflow** and the workflow, of this file or another Arazzo file of the collection. The arrow ends in a box below **End of workflow**: **↗ Continues in «…»**. Control does not come back.

```yaml
onFailure:
  - name: on500
    type: goto
    workflowId: reportProblem
    criteria:
      - condition: $statusCode == 500
```

For a workflow of another Arazzo file, Luvin adds that file to the sources and writes `$sourceDescriptions.<source>.<workflowId>`.

### Detour when the step passes and a condition holds

The species is legendary, and you want to skip to another step. `getSpecies` has the output `isLegendary`, which reads `$response.body#/is_legendary`.

<Steps>
1. On the card of `getSpecies`, click **＋ Detour if it passes and a condition holds**.
2. In **If the value**, choose the output `isLegendary`, and type `true` after **is**.
3. Choose **Go to another step**, **Continue in another workflow** or **End successfully**, and click **Add**.
</Steps>

```yaml
onSuccess:
  - name: ifIs_legendary
    type: goto
    stepId: getLegend
    criteria:
      - condition: $response.body#/is_legendary == true
```

If a detour skips a step whose data a later step uses, **⚠ to review** warns you. Runnable example: [Retry, jump and end on errors](/recipes/error-branches/).

### A rule for every step

A 429 can happen in any step. Instead of a route in each one, click **Start** and, under **If any step fails**, click **＋ Rule for every step**. Each card reminds you: **If none of these applies, it uses the Start rules (429)**.

```yaml
failureActions:
  - name: retry429
    type: retry
    retryAfter: 2
    retryLimit: 3
    criteria:
      - condition: $statusCode == 429
```

Details: [The Routes panel and rules for every step](/design/routes-panel/).

### Order and check the routes

The **Success and routes** tab of a step lists its routes in order: the first that matches wins. Use **↑** and **↓** to reorder, **✎** to change and **✕** to remove. The chip **⚠ to review** lists the routes that skip data, go to a step that is gone, loop with no limit, or never match. See [To review](/design/review/).

## Repeat a step or wait

### Go through every page

Click **＋ Step**, then **Go through every page** under **Patterns · standard Arazzo**, then the operation. The step repeats while the response has a next page, and sends the cursor of the previous round.

```yaml
onSuccess:
  - name: siguientePagina
    type: goto
    stepId: listProducts
    criteria:
      - condition: $response.body#/nextCursor != null
```

APIs that page with `skip` and `limit` cannot be looped this way in Arazzo. Details: [Standard Arazzo patterns](/design/patterns/).

### Wait until a job finishes

Choose **Wait until it finishes** and the operation that reads the job. The step passes when `status` says `done`, or when a field such as `completed` is `true`, and retries every 2 seconds, up to 10 times, while it is not.

```yaml
successCriteria:
  - condition: $statusCode == 200
  - condition: $response.body#/completed == true
onFailure:
  - name: mientrasPendiente
    type: retry
    retryAfter: 2
    retryLimit: 10
    criteria:
      - condition: $response.body#/completed == false
```

Details: [Standard Arazzo patterns](/design/patterns/#wait-until-it-finishes).

## Use other workflows

### Depend on another workflow of the same file or of another file

`placeOrder` needs the token that the `login` workflow returns, and `login` is in `auth.arazzo.yaml`.

<Steps>
1. Click **Start**. Under **Depends on**, open **Add a workflow…**.
2. Choose a workflow under **In this file** or under the group of another file, such as **In auth.arazzo.yaml**.
3. A **⇡ Depends on** card appears above **Start** with the outputs of that workflow. Use them from the **Source** list of any value, or drag their dot.
</Steps>

![The Add a workflow list with the groups In this file and In auth.arazzo.yaml](/media/en/design-depends-options.webp)

![The Depends on card above Start: the login workflow of auth.arazzo.yaml and its output token](/media/en/design-depends-card.webp)

```yaml
sourceDescriptions:
  - { name: auth, url: ./auth.arazzo.yaml, type: arazzo }
workflows:
  - workflowId: placeOrder
    dependsOn: [$sourceDescriptions.auth.login]
```

For a workflow of the same file, `dependsOn` has only its id: `dependsOn: [browseProducts]`. Details: [Workflows that use other workflows](/design/dependencies/).

### Call a workflow as a step

Click **＋ Step** and choose the workflow under **Workflows in this Arazzo** (or **From other Arazzo files**). The new step lists the inputs of that workflow under **Workflow inputs**, wired like any other value, and its outputs. On the card, **▸ See its N steps** lists the steps it runs.

![The panel of a step that calls the workflow browseProducts: its input limit and its outputs sku and price](/media/en/design-call-workflow.webp)

<video controls muted playsinline preload="metadata" poster="/media/en/design-depends.webp" src="/media/en/design-depends.mp4"></video>

```yaml
- stepId: browseProducts
  workflowId: browseProducts
  parameters:
    - { name: limit, value: $inputs.limit }
  outputs:
    sku: $outputs.sku
    price: $outputs.price
```

## Define once, use in several steps

### Reusable failure routes and parameters

<Steps>
1. Give a step a failure route on one status, for example **Retry** on **429**, or give a parameter a value.
2. Save it: **Save as reusable** under the route in the **Success and routes** tab, or ♻ on the parameter in the **Data** tab. Type a name and save.
3. Apply it to another step: drag it from **Reusables**, in the **Start** panel, onto the card, or pick it under **Or apply a reusable:** in the route editor.
4. Click it in **Start** to edit it once for every step. **Used in** lists the steps.
</Steps>

![The panel of the reusable unauthorized of PayPal: ends the workflow on a 401 and is used in five steps](/media/en/design-reusable-panel.webp)

<video controls muted playsinline preload="metadata" poster="/media/en/design-reusables.webp" src="/media/en/design-reusables.mp4"></video>

```yaml
components:
  failureActions:
    tooManyRequests:
      name: tooManyRequests
      type: retry
      retryAfter: 1
      retryLimit: 3
      criteria:
        - condition: $statusCode == 429
# in each step:
onFailure:
  - reference: $components.failureActions.tooManyRequests
```

On the card, a reusable route has the mark ♻. Details: [Reusables](/design/reusables/).

## Messages and events

### Send and receive messages

<Aside type="caution">
Messaging steps are always simulated. Luvin does not connect to brokers (Kafka, AMQP, MQTT…): the step uses the examples of the AsyncAPI contract, also when you run against the real API.
</Aside>

Add the AsyncAPI operation with **＋ Step**, as with any operation: it is tagged **SEND** or **RECEIVE**. Luvin writes `action`, the correlation id and, for a receive, `timeout: 5000`. Outputs are edited in the panel. Criteria on the message, such as the one below, and failure routes are written in the YAML tab. See [Add a messaging step](/design/messaging/#add-a-messaging-step).

![The panel of awaitConfirmation, a receive step, with its criterion on the message and its output entryNumber](/media/en/design-messaging-receive.webp)

```yaml
- stepId: awaitConfirmation
  channelPath: '{$sourceDescriptions.pokedexEvents.url}#/channels/sightingConfirmed'
  action: receive
  correlationId: $inputs.correlationId
  timeout: 5000
  successCriteria:
    - condition: $message.payload#/status == 'CONFIRMED'
```

Details: [Messaging steps](/design/messaging/).

## Without a contract

### Build from saved requests

<Steps>
1. Create a workflow with **+** › **New Arazzo**.
2. On the empty canvas, click **Build from the collection's requests** and click your requests in order. You can also drag them from the tree of the sidebar.
3. Click a step and **Try this step**, or run the workflow once against the real API, so Luvin learns the responses.
4. The bar **Luvin found 1 connection(s) between steps** proposes the connections. Click **Connect**.
</Steps>

![The bar Luvin found 1 connection(s) between steps: the orderId of getOrder would come from the id of createOrder](/media/en/design-connections-bar.webp)

### Mark the required fields of a request

A request does not say which fields the API requires. Its card shows **required not marked**, and a bar above the canvas says how many steps are missing the answer, with **Mark**. Click **Mark**, tick the required fields and click **Save**. To change it later, click the step and then **Required fields (n)** at the top of its panel.

![The dialog What does the API require in «Create order»? with customer ticked as required](/media/en/design-required-fields.webp)

```yaml title="requests/create-order.request.yaml"
requiredFields:
  - body:customer
```

Details: [Mark the required fields of a request](/design/required-fields/).

## Fix a workflow

### Complete the missing data

After a contract changes, or after you edit the YAML, a step may use an input the workflow does not declare, or not send something the contract requires. The bar **This workflow is missing data** says what. Click **Complete**. **↶ Undo** reverts it.

![The bar This workflow is missing data: it uses inputs the workflow does not declare, username, with the Complete button](/media/en/design-gaps-bar.webp)

### Edit the YAML by hand

<Steps>
1. Open the **YAML** tab, or **\{ \} YAML** › **Edit in YAML**. It is the same file the canvas edits.
2. Type. After `$`, `$steps.` or `$inputs.` the editor suggests what exists.
3. Check the badge above the text and the **Problems** list below it.
4. Go back to **Design**. What you wrote stays, also after you change other things on the canvas.
</Steps>
