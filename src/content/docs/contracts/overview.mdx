A contract is a file that describes an API: which calls it has, what each one receives and what it answers. Luvin reads two kinds, **OpenAPI** (REST APIs) and **AsyncAPI** (messages and events). Without a contract, Luvin does not know which operations exist, so you cannot design a workflow from them.

Luvin never changes a contract on its own. You design, run and simulate workflows, and the contract stays as you wrote it. It changes only when you edit it.

## Example: one operation of the PokéAPI contract

This is a trimmed fragment of the bundled `examples/pokemon/pokeapi.openapi.yaml`:

```yaml title="pokeapi.openapi.yaml"
servers:
  - url: https://pokeapi.co/api/v2
paths:
  /pokemon/{idOrName}:
    get:
      operationId: getPokemon
      summary: Consulta un Pokémon
      parameters:
        - $ref: '#/components/parameters/IdOrName'
      responses:
        '200':
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Pokemon' }
              example:
                id: 25
                name: pikachu
                types:
                  - slot: 1
                    type: { name: electric }
        '404':
          $ref: '#/components/responses/NotFound'
```

This one operation is what Luvin needs to design, run and simulate a call:

| In the contract | What Luvin does with it |
|---|---|
| `operationId: getPokemon` | Lists it in the **Design** tab, ready to drag onto the canvas. The new step is called `getPokemon`. |
| `summary` | Becomes the description of the step. |
| `parameters` | Asks for `idOrName` in the step. Because it is required and nothing gives it a value, it becomes an input of the workflow. |
| `servers` | Fills the base URL `pokeapi` of each environment with `https://pokeapi.co/api/v2`. |
| `200` with its `schema` | Sets the success criterion `$statusCode == 200`, offers the fields of the response as outputs, and checks every real response against the schema. |
| `example` of the `200` | Is the answer in **Simulation** and in a mock server. |
| `404` | Is offered as an error the step can handle, for example to end the workflow. |

## What Luvin reads from a contract

| Part of the contract | Where you see it | Read more |
|---|---|---|
| `paths` and their operations | The **＋ Step** search of the **Design** tab. Each operation becomes a step. | [From operation to step](/contracts/operations-and-steps/) |
| `parameters` and `requestBody` | The parameters and body of each step, the inputs of the workflow and the generated cases. | [Schemas, inputs and cases](/contracts/schemas-and-cases/) |
| `responses` and their schemas | Success criteria, error branches, outputs and the check of each response. | [Does the response match the contract?](/contracts/response-check/) |
| `example` and `examples` | **Simulation**, mock servers, **Try it out**, generated requests and the starting values of inputs. | [Examples, simulation and mocks](/contracts/examples/) |
| `servers` | The **Base URLs** of every environment. | [Servers and credentials](/contracts/servers-and-credentials/) |
| `security` and `securitySchemes` | The **Credentials** of every environment, and the **Without credentials** case. | [Servers and credentials](/contracts/servers-and-credentials/) |
| `tags` | The **＋ Step** search, and one folder per tag when you generate requests. | [Generate requests from a contract](/requests/generate-from-contract/) |
| AsyncAPI `channels`, `operations` and messages | Send and receive steps, always simulated. | [AsyncAPI contracts](/contracts/asyncapi/) |
| `$ref` to other files | The parts that live in other files, joined into one contract. | [References between files](/contracts/references/) |

## How a workflow finds its contract

A workflow file (the Arazzo file) lists the contracts it uses in `sourceDescriptions`. Each one has a name, an address and a type:

```yaml title="pokemon.arazzo.yaml"
sourceDescriptions:
  - name: pokeapi
    url: ./pokeapi.openapi.yaml
    type: openapi
  - name: pokedexEvents
    url: ./pokedex-events.asyncapi.yaml
    type: asyncapi
```

The steps use that name: `operationId: $sourceDescriptions.pokeapi.getPokemon`. The base URL of the environment and the credentials are also stored under that name, so `pokeapi` is the name you see in the **Contracts** list, in **＋ Step** and in the environment.

Luvin matches each address with a file of the collection by its file name. You do not write these lines by hand: a new workflow file lists every contract of the collection for you. See [How a workflow finds its file](/contracts/add/#how-a-workflow-finds-its-file).

## Supported versions

| Kind | Versions | With another version |
|---|---|---|
| OpenAPI | 3.x, for example `openapi: 3.0.3` | Swagger 2.0 opens and is listed, with the warning *This is Swagger 2.0: Luvin works with OpenAPI 3.x; consider migrating it.* Parts of it may not work as expected. |
| AsyncAPI | 2.x and 3.x | The editor warns *AsyncAPI version “x”: 2.x or 3.x is expected.* |

Luvin tells the kind of a file from its first fields: `openapi:` or `swagger:` for OpenAPI, `asyncapi:` for AsyncAPI. A YAML or JSON file with neither, such as a file of shared schemas, is listed as `schemas`. The file name does not decide the kind, but names such as `pokeapi.openapi.yaml` make the list easier to read.

<Aside type="tip">
You can test an API without a contract: send single requests and drag them into a workflow. Luvin then builds a small contract from your requests by itself. See [Workflows from requests](/design/from-requests/).
</Aside>
