Many APIs return lists: the cards of a customer, the products of a catalog. When a later step needs data from that list, Luvin pauses the run and shows you what came back, so you choose what to test with.

<video controls muted playsinline preload="metadata" poster="/media/en/list-pick.webp" src="/media/en/list-pick.mp4"></video>

## Example: Pokemon card against the real API

The first step of **Pokemon card** returns two lists that later steps use: `types` (1 item) and `abilities` (2 items). Against the real API the run pauses for both, also for `types` with its single item: you see what the service returned and confirm what the run goes on with. In Simulation it pauses only for `abilities`, the list with something to choose.

<Steps>
1. Choose **Real API** and press **Run**.
2. The dialog opens for `types`, with its single item. Press **Continue with this item**.
3. It opens again for `abilities`, which has two items. Click the one you want and press **Continue with this item**.
</Steps>

Against the real API the dialog appears for every list later steps use, even with one item. In **Simulation** it appears only when the list has two or more items. For a step-by-step version, see the recipe [Choose an item from a list](/recipes/list-pick/).

## Choose and continue

<Steps>
1. Run the case. After the step that returns the list, a dialog opens with the title **Which item of the list do you want to test with?**
2. Read the top of the dialog: which step returned the list and how many items, the **Case** that is running, and **Goes to**, the later steps and parameters that receive the data.
3. Click the row of the item you want.
4. Press **Continue with this item**. The next steps run with it.
</Steps>

![The dialog to choose one item from the list a step returned](/media/en/list-pick.webp)

The table shows the real items of the list:

- Columns marked **used** hold the values that go to the next steps.
- With more than 8 items there is a search box, **Search the list…**. It also searches the fields that are not shown as columns.
- If the items have more fields than fit in the table, the header says how many, for example **+4 fields**. **See all** on a row opens the complete item.
- <Badge text="Max 200 items" variant="caution" /> The table shows up to 200 items. Search to find the rest.

## What you can choose depends on the design

| How the workflow uses the list | What the dialog offers |
|---|---|
| A value of one item goes to a path, query or header parameter | One item |
| A value of one item goes inside a list of the next request's body | Several items, or **Send the whole list**. The body gets one entry per item |
| The whole list goes to a step that takes lists | **Send the whole list**, or **Choose items** to send only some |
| The whole list is connected to single-value parameters | One item. Each parameter receives a field of that item |

![The dialog offering to send the whole list or to choose items](/media/en/list-pick-many.webp)

When you tick several items, the button says **Continue with N chosen**. If a later step takes a single value, it gets the first of the chosen ones, and the dialog says so.

In the last case of the table, the dialog adds **What each step receives from the item you choose**. Luvin matches each parameter to the field with a similar name: `bank` takes the item's `bank`. To use another field, change it in the dropdown next to the parameter.

## Set it up in the design

<Steps>
1. In the **Design** tab, click the step that needs the data.
2. In the **Data** tab of the step panel, under **Receives**, open the source of the parameter and choose the field of the list from the previous step, for example `activeCreditCards/bank`. It says *from a list: you choose which at run time*.
3. Run the case. The dialog appears after the step that returns the list.
</Steps>

A field that comes from a list is named without its position: `activeCreditCards/bank`, not `activeCreditCards/0/bank`. See [Wire data between steps](/design/wire-data/).

## A list returned by a called workflow

A step can call another workflow, for example one you reuse to get a customer's cards. If that workflow returns a list as an output, and the next step puts it in a single-value parameter, the run pauses the same way. It's the step that called the workflow that asks, and each parameter receives its field of the chosen item: `bank` gets the `bank` of the chosen card, `id` gets the `id` of the chosen benefit. Without someone to choose (the Runner or a load test), the first item is used.

## Several cases at once

When you run several cases, the dialog offers **Use this choice for the other cases in this run**. Leave it ticked to be asked once. Untick it to choose in every case. If a later case gets a list without the items you chose, the dialog asks again.

Luvin remembers your last choice and proposes it the next time you run.

## Saved rules for next times

So that the dialog does not ask every time, save a rule. The rule chooses for you in your next runs, and it is what the [Runner](/runner/workflows/) uses, where nobody is there to answer.

<Steps>
1. Run the case. The dialog opens.
2. At the bottom, open the list **Next times:** and choose a rule.
3. Choose the item for this run as always and press **Continue with this item**.
</Steps>

![The bottom of the dialog with the Next times: list open: Ask me, Use the one in the design, Pick one at random, A different one each iteration and The one where…](/media/en/list-pick-rule.webp)

| Rule | What it chooses |
|---|---|
| **Ask me** | Nothing is saved: the dialog asks again. In the Runner, the item in the design is used. |
| **Use the one in the design** | The item the workflow design points to. |
| **Pick one at random** | Any item, different each time. |
| **A different one each iteration** | The first item in the first iteration of the Runner, the second in the second, and so on. When you run several cases by hand, a different one for each case. |
| **The one where…** | The first item that meets a condition. Choose the **Field**, the **Condition** (**is**, **is not**, **contains**, **is greater than**, **is less than**) and the **Value**. |
| **All of them** | The whole list. Only when the next steps can take several items. |

The rule is saved in the step of the Arazzo file, under the extension `x-luvin-pick`. Other Arazzo tools ignore it.

```yaml title="shop.arazzo.yaml" {3-8}
- stepId: getCustomer
  operationId: getCustomer
  x-luvin-pick:
    "#/activeCreditCards":
      rule: match
      field: bank
      op: eq
      value: Banco Sur
```

With a saved rule, the dialog no longer appears for that list, in your runs or in the Runner. The workflows Runner shows the lists and their rules under **Lists in the responses**. To delete a rule, press **Remove** next to it. See [Run workflows](/runner/workflows/#lists-in-the-responses).

### When "The one where…" finds nothing

If no item meets the condition:

- In the Runner, and in a performance test, the step fails with *No item in the list (3) matches the rule: bank is Banco Sur.* The run does not go on with another item as if nothing happened.
- When you run by hand, the dialog asks you, as if there were no rule.

## What is recorded

The step that returned the list keeps a note, **Chosen at run time**. For example: *From the list abilities, the run continued with "lightning-rod" (item 2 of 2).* Below it, the note says which value each parameter received.

## When the dialog does not appear

- If the list has a single item, in **Simulation**. The run goes on with it, and the step keeps a note: *From the list: The list types had a single item ("…"): it was used.* Against the **Real API** the dialog does appear, so you confirm what the service returned.
- If the step has a saved rule for that list. See [Saved rules for next times](#saved-rules-for-next-times).
- In the [Runner](/runner/workflows/). It never stops to ask: it uses the saved rule or the item in the design.
- In a route probe, **▷ Probe** on the canvas. Like the Runner, it uses the saved rule or the item the design points to. See [Probe routes and coverage](/test/probe-routes/).
- If the list comes back empty.
- If no later step uses data from the list.
- If the step that returns the list failed.

When you run only a step, up to a step or from a step, the dialog does appear, as in a normal run. See [Debug a workflow](/test/debug/#run-only-up-to-or-from-a-step).

**Stop run**, in the dialog, cancels the run.
