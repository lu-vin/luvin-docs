Luvin is a tool for **API workflow engineering**. When a business process spans several APIs, Luvin lets you design that process visually, see how the data moves from one call to the next, test its scenarios, and share evidence that it works.

Read this page to decide whether it fits your work, then follow the [quick start](/get-started/quick-start/).

## The problem

A single screen of an app usually depends on several APIs called in order. Take a shop:

<Steps>

1. You log in on API **A** and get a token.
2. You call API **B** with that token and get the customer.
3. You call API **C** with the customer's id and get their orders.

</Steps>

To test **C**, you first call **A** and **B** by hand and copy values from one response into the next request. Every time. And nobody can quickly say which APIs that screen depends on, or how the data moves between them.

Luvin removes those manual calls. You describe the chain once, as a **workflow**: a sequence of API calls where each **step** can use data from the previous ones. Luvin then runs the whole chain for you and tells you, in plain words, whether it worked.

## Example: the Pokémon card

The bundled Pokédex workflow chains four calls to the public PokéAPI. Each arrow is data that Luvin wires for you:

```text
getPokemon ── id ─────────────▶ getSpecies
           ── mainType ───────▶ getWeakness
           ── firstAbility ───▶ getAbility
```

You enter one value, `pokemon: pikachu`. Luvin runs the four steps, passes each result to the next and tells you whether the chain worked. Try it in the [quick start](/get-started/quick-start/).

## How it works

<Steps>

1. **Bring your contracts.** A contract is the OpenAPI or AsyncAPI file that describes an API. Add the contracts of the APIs involved, or import your Postman or Bruno collection.
2. **Design the workflow visually.** Drag the operations onto a canvas. Luvin connects the data between operations automatically, by rules and with no AI involved. For example, a `customerId` parameter is connected to the `id` that the "create customer" step returned.
3. **Test its scenarios.** Luvin generates **cases** (a case is one run of the workflow with given inputs): the happy path, invalid inputs, calls without credentials and one case per error path. Add your own and run them against the real API, or in **simulation**, where Luvin answers from the examples in the contract without calling anything. A case that passes in simulation proves the logic of the workflow, not your API: each result says whether it ran against your API or in simulation.
4. **Share the evidence.** Export the results as an HTML report anyone can open. The workflow itself is saved as a standard [Arazzo](https://spec.openapis.org/arazzo/latest.html) file, the OpenAPI Initiative's open format for sequences of API calls: it is yours, readable as YAML, kept in git and portable to other Arazzo tools. Your workflow isn't locked into Luvin: you can review it in a pull request, version it next to your code and run it in a CI runner that reads Arazzo.

</Steps>

<Aside type="tip" title="No contracts, or Arazzo files already written?">
If you already have Arazzo files, open them and they work the same way. If you have no contracts, import your Postman or Bruno collection and drag its requests onto the canvas. See [Import your existing work](/get-started/import/).
</Aside>

## What you can test

Logging a customer in and keeping the session alive, placing an order, paying with OAuth 2.0, signing up with fresh data, recovering from errors. Each scenario has a runnable example: see [What you can test with Luvin](/get-started/use-cases/).

## Who it is for

| You are | Luvin helps you |
|---|---|
| An integration or QA engineer | Stop calling each API by hand. You get generated negative cases, a clear verdict per case and every request in Dev Tools. |
| On an API product or partner team | Show that a workflow made of several APIs works end to end, with a report to share. |
| A product manager or in a business role | Try a workflow with your own data in a simple interface, with no command line and no test code. |
| An API designer | See how your APIs connect and check workflows against the real contracts. |

## Scope and limits

Luvin is for designing, debugging and demonstrating processes that span several APIs. It does not run integrations in production and it is not a CI runner: the workflows it saves are standard Arazzo files, which you can take to your pipeline. See [What Luvin does not do](/reference/faq/#what-does-luvin-not-do).

<Aside type="caution" title="Know these limits before you plan a test">
- **A pass in Simulation is not a pass against your API.** Simulation answers with the contract's examples. To prove the API, run with **Real API**.
- **Messaging steps are always simulated.** AsyncAPI `send` and `receive` steps answer from the contract, even when you run against the real API. Luvin does not connect to Kafka, AMQP or MQTT yet, so it cannot prove an asynchronous integration end to end.

See every [known limitation](/reference/limitations/).
</Aside>
